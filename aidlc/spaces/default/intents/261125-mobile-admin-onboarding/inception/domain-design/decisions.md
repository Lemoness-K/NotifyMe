# 모바일 최초 관리자 등록 아키텍처 결정

## ADR-039: 명시적인 설치 주기와 일회성 초기 등록

### Context

완료된 `D-074` 최초 관리자 CLI는 현재 가구의 존재를 검사한다. 사용자 요구사항 `FR11.1`과 `NFR12`는 신규 설치나 승인된 재설정의 의도와 장애·복원·가구 종료를 구분해야 한다. 기존 운영 런타임은 일반 DB 설정 경로와 별도 활성화 세대를 구분하고 복원을 새 세대로 게시한다. 요구사항 검토 R-01은 등록 횟수의 기준을 Pi가 아닌 설정 주기로 명료화하라고 지적했다.

### Decision

- 설치 준비 또는 별도로 승인된 초기화가 **검증한 신규 SQLite 대상**에만 고유한 설정 주기를 발급한다. 배포 시 이 준비를 수행하면 이후 일반 재기동과 휴대폰 첫 설정은 수동 Firebase 토큰이나 SSH 단계 없이 진행한다. 이미 존재하는 DB와 미확인 경로는 업그레이드 시 닫힌 상태로 취급한다. 비어 있던 기존 DB를 자동 승격하지 않는다.
- 긍정적인 자격은 DB 바깥의 운영자 보호 기록에 보관하고, SQLite 안의 설치 식별자와 관리형 활성화 세대가 일치할 때만 효력이 있다. 없거나 읽을 수 없거나 불일치하는 상태, DB 장애, 복원 진행·완료, 가구 종료는 모두 새 후보와 확인을 차단한다. 정상 시작·마이그레이션·가구 종료는 새 주기를 만들지 않는다.
- 복원은 후보 DB 준비 전에 설정 허용을 닫고 후보 자격 증명을 무효화한다. 새 세대를 활성화해도 등록을 다시 열지 않는다. 백업에 등록 가능했던 이전 주기의 상태가 포함된 경우에도 동일하다. 새 등록은 운영자가 승인한 별도 신규 설치 준비에서만 열린다.
- 확인의 영속 경계를 두 단계로 둔다. 등록 트랜잭션 전에 운영자 보호 기록에 현재 주기와 후보의 확인 진행을 내구성 있게 기록하고, 같은 주기에서 다른 쓰기가 경쟁하지 않도록 직렬화한다. 한 SQLite 트랜잭션에서 후보·주기를 재검증하고 내부 사용자 연결, 최초 가구, 첫 ADMIN 멤버십과 완료 기록을 확정한다. 성공 후 운영자 보호 기록을 봉인한다. 등록 완료를 증명하는 커밋과 그 기록이 유실되거나 모호할 때에는 새 후보 획득을 차단한다.
- 재시작 시 진행 기록은 같은 주기·후보의 DB 완료 증거를 검증해 봉인할 수 있다. 커밋 결과를 확인할 수 없는 경우 차단을 유지한다. 완료 없이 확실히 롤백됐고 동일한 활성 DB임을 확인한 경우에만 정상 요청에서 원래 후보의 남은 유효기간을 유지한다. 장애 복구 절차는 대상 확인과 운영자 승인으로 분리한다. 완료된 가구나 기존 세션을 장애 회복을 위해 제거하지 않는다.
- 지원되는 운영 환경에서 기존 `admin:bootstrap` 직접 등록 경로가 이 기준을 우회하지 않도록 차단한다. 기존 DB 로그인과 `D-023` 지정 이메일 초대는 기존 가구, 연결된 사용자와 멤버십을 기준으로 지속한다.

### Consequences

- 같은 Pi라도 승인된 새 설정 주기에는 새 등록이 한 번 가능하다. 이전 주기 후보는 이를 확인할 수 없다. 새 가구 한 건과 최초 관리자 멤버십 한 건이 함께 커밋된다.
- 운영자 보호 기록과 DB 식별자 불일치는 정상 운영 중 자동 등록 대신 차단·진단으로 이어진다. 비정상 종료의 드문 경우 운영상의 복구 절차가 필요할 수 있다.
- 후보 변경과 최종 확인의 이중 제출, 준비·복원·종료 상태 간 교차, 장애 직전·직후의 동작을 격리된 DB에서 테스트한다.

### Alternatives Rejected

- 가구 수가 0일 때 자동으로 열기. 종료·빈 백업·DB 경로 변경이 신규 설치로 오인될 수 있다.
- SQLite 안에만 허용 상태 저장. 트랜잭션은 편하지만 이전 백업을 복원하면 열렸던 상태도 되살아날 수 있다.
- 환경 변수 하나로 계속 허용. 초기화 성공이나 복원과 함께 일회성을 보장하기 어렵다.

## ADR-040: 운영자 전용 Tailscale과 확인 전 후보 권한

### Context

`Q-071` 최초 설정 중 접근 범위에 대해 현행 Tailscale로 접속하는 사람은 관리자뿐이라고 확인했다. `FR11.2`, `FR11.4`, `NFR13`과 요구사항 검토 R-02를 함께 만족해야 한다.

### Decision

- 현재 배포는 운영자만 도달할 수 있는 Tailscale 내부 HTTPS 경계를 유지한다. 해당 경계의 설정 가능 상태에서 처음으로 기존 Google/Firebase 증명 검증과 후보 예약을 성공한 계정에만 확인 화면을 표시한다. 기존 Caddy와 NestJS 경로를 우회해 공개되지 않도록 운영 가이드에 점검을 포함한다. 가입 후보에게 Tailscale 사용자 이름과 Google 계정의 동일성을 요구하지 않는다.
- 후보는 한 주기에 동시 한 명이며 기본 10분 동안 유효하다. 짧은 설정 전용 자격 증명은 주기·후보·확인된 계정에 결합하며 일반 세션에서 수락하지 않는다. 같은 브라우저에서 새로고침하면 유효한 후보를 계속 표시한다. 같은 계정이 다시 검증되면 남은 기간만 사용할 수 있다. 재진입·새로고침·탭 닫기를 이유로 유효기간을 연장하지 않는다.
- 취소는 후보를 즉시 해제하고 그 자격을 무효화한다. 취소 응답을 잃거나 창을 닫아 취소가 전달되지 않으면 원래 후보 만료 시 다시 신청할 수 있다. 다른 후보를 기다리는 화면에는 선점자의 계정을 표시하지 않는다. 후보는 자신의 설정 상태 조회·확인·취소만 할 수 있다.
- 확인과 취소가 겹치면 전환을 하나씩 처리한다. 취소가 먼저 확정되면 그 후보의 확인은 실패한다. 확인이 커밋된 후 응답만 유실되면 등록을 닫은 채 유지하며, 같은 검증 계정은 기존 가구로 이어진다. 성공 응답에서는 현재 로그인으로 정상 세션을 발급하고 가구 리마인더 화면을 연다.
- 공개 인터넷에서는 이 방식의 등록을 사용하지 않는다. 외부 노출 전 운영자 증명 또는 사전 승인과 같은 별도 보호 정책을 결정한다. 현재 모바일 설정에는 앱 수동 토큰을 추가하지 않는다.

### Consequences

- 현행 운영자는 Google 로그인과 계정 확인으로 설정할 수 있다. Tailscale 도달 범위를 넓히기 전에 정책을 다시 검토한다.
- 서버 시간 기준 10분이 지나면 같은 계정이나 다른 계정이 새로 인증할 수 있다. 중간 응답 유실, 다중 탭, 만료 경계, 계정 전환 및 일반 API 거부를 검증한다.
- 후보의 계정 표시는 검증된 Google 계정의 이메일로 한정한다. 브라우저 설정 자격 증명과 제공자 토큰을 로그에 남기지 않는다.

### Alternatives Rejected

- 브라우저 메모리만으로 후보를 유지. 탭이나 계정 경쟁을 서버에서 일관되게 처리할 수 없다.
- 별도 운영자 코드나 Google 계정 사전 입력을 매번 요구. 현재 운영자 전용 접근 범위에는 추가 절차의 비용이 크다.
- 최초 로그인만으로 곧바로 ADMIN 부여. 사용자가 계정을 점검하고 취소할 기회가 사라진다.
