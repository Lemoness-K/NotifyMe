# U5 운영·백업·복구 기능 설계

## Sources

U5의 `unit-of-work.md` 배정과 `stories.md`의 US2.7·US8.1~US8.5, `requirements.md`의 FR9·FR10, `components.md`의 운영 책임과 `contract-summary.md`의 `recovery-delete-journal-v1`을 적용한다. 운영·복구 제약은 D-025·D-053·D-058·D-077·D-092·D-098, `docs/06-deployment-and-operations.md`, `docs/07-security-and-privacy.md` 및 ADR-026에 근거한다.

## 운영 진단과 기록

- 운영자는 호스트의 권한이 있는 명령으로 서비스 상태, 로컬 헬스, 디스크·메모리, 최근 백업 상태를 조회한다. API·Worker는 표준 출력·오류와 journald를 사용한다. 기존 공개 HTTPS 경로에는 운영 명령과 내부 헬스를 추가하지 않는다.
- Q-070에 따라 주간 요약과 감지 즉시 생성하는 장애 기록을 로컬에 제공한다. 서버 측 운영 설정 두 값으로 각각 활성화하며 기본은 꺼짐이다. 꺼짐은 새 기록 생성을 멈추고 기본 상태 조회와 백업은 계속 제공한다. 이미 남은 로그는 호스트 보존 정책을 따른다.
- 주간 요약은 운영 시간대의 같은 주에 한 건을 기록한다. 서비스 상태, 최근 백업 결과 및 장애 건수만 포함한다. 로컬 헬스 실패가 감지되면 장애 상태로 전이할 때 한 건을 기록하고 같은 상태의 반복 확인은 합친다. 복구를 확인하면 다음 장애를 다시 기록할 수 있다. 검사기 자체의 실패는 진단 실패로 기록한다. 호스트 전원·망 중단의 외부 수신과 기존 외부 채널 연결은 후속이다.

## 일관 백업과 보존

1. 기존 U3 삭제 원장 배타 경계에서 새 삭제 요청을 막고 기존 요청의 종결 상태와 운영 DB의 커밋 증거를 검증한다. 처음 처리한 삭제가 DB 변경 전에 권한 거절된 것이 확인되면 ABORTED로 종결한다. 같은 요청의 재시도에서는 과거 증거를 확인하며 권한 거절만으로 ABORTED를 만들지 않는다. U4 설치 정리 실패가 이 원장 조정을 건너뛰게 하지 않는다.
2. 같은 경계에서 SQLite 일관 사본을 생성한다. 원장에 기록된 COMMITTED가 사본에 반영됐으며 `includedThrough`까지 누락·미확정이 없음을 확인한다. 배타권 만료, 사본 오류, 증거 불일치는 기준점 발행을 막는다. 원본 main 파일만 복사하지 않는다.
3. 사본을 암호화하고 스냅샷 ID, 내용 해시, 스키마와 `includedThrough`를 인증된 백업 정보에 묶어 원자적으로 게시한다. 키와 인증된 원장 기준점의 증거를 백업 파일과 분리한다. 작업 결과에는 시작·종료·성공 여부와 분류한 오류만 남긴다. 중단으로 남은 임시 산출물은 복구 후보에 포함하지 않는다.
4. DB 자동 백업은 매일 실행한다. 보관본은 최대 30일이다. 백업 게시·만료와 원장 정리는 같은 배타 경계에서 기록한다. 가장 오래된 선택 가능 백업의 기준점 이후는 삭제하지 않는다. 물리 삭제 전에 만료 백업을 목록에서 내리고, 진행 중인 복원이 읽는 경계도 보호한다. 보호된 위치와 최대 보존이 충돌하면 해당 백업을 먼저 복구 불가로 전환하고, 미확정 원장의 임의 삭제로 해소하지 않는다. 카탈로그나 정리 위치가 확인되지 않으면 원장 정리를 보류하고 정확한 복구 가능 범위를 검증한다. 운영 전체 백업 주기는 DS-008에서 다룬다.

## 복구에 사용하는 최신 원장 경계

삭제 경계의 권위 있는 저장소를 운영 DB·백업·원장 사본과 독립적으로 유지한다. 최신 증거에는 원장 계보 ID와 그 끝의 단조 위치, 해당 이력의 인증된 누적 증거를 포함한다. 선택한 원장 파일의 ID나 마지막 행으로 최신성을 추정하지 않는다. 이전과 동일한 계보의 유효한 사본도 권위 있는 최신 증거보다 짧거나 다른 이력을 가지면 차단한다. 원래 호스트를 잃은 경우에도 해당 저장소의 최신성을 독립적으로 확인해야 하며, 이것이 불가능하면 공개 복구를 진행할 수 없다.

U3의 삭제는 먼저 REQUESTED를 내구 기록하고 현재 끝을 독립 증거에 반영한 뒤 운영 DB를 변경한다. 종결 결과 역시 내구 기록과 독립 증거 반영을 완료한 뒤 성공을 반환한다. 운영 DB 변경 후 중단되면 확인 가능한 커밋 증거로 재조정한다. 증거가 없는 REQUESTED나 이전 독립 증거와 다른 원장은 확인 전까지 새 백업 기준점 발행과 복구 재개를 막는다.

## 격리 복원 및 서비스 재개

1. 전용 운영 절차에서 공개 제공과 원본 쓰기를 중단하고 재부팅에도 유지되는 공개 차단 상태를 먼저 저장한다. 독립 저장소의 최신 증거와 일치하는 원장 이력에서 `recoverThrough`를 고정한다. 별도 복구 경로에만 복호화하고 스냅샷 인증·내용 해시·스키마를 검증한다.
2. `includedThrough` 뒤부터 `recoverThrough`까지 인증된 원장의 연속성과 각 요청의 종결을 확인한다. COMMITTED만 가구·업무 경계로 멱등 재적용하고 삭제된 업무와 연결 이력이 보이지 않는지 확인한다. ABORTED는 재적용하지 않는다. 누락·변조·미확정 또는 대상 불일치는 재개를 중지한다.
3. 격리 DB에서 SQLite 무결성, 외래 키 검사, 지원되는 마이그레이션, 기본 인증·가구 조회와 삭제 항목 부재를 검증한다. U4의 기존 기기 커서가 과거 데이터와 다시 일치하지 않도록 현재 운영 세대와 다른 서버 epoch를 준비한다. 인증·발송·스케줄 외부 효과가 격리 환경에서 실행되지 않게 한다.
4. 검증된 실행 ID·격리 사본 지문·대상 DB 경로·새 epoch를 한 활성 상태에 묶는다. 최초 쓰기 전에 사본과 경계를 검사한 뒤 단일 내구 전환으로 공개를 허용한다. systemd는 미완료 전환이나 이전 DB와 새 epoch의 혼합을 허용하지 않는다. 이후 일반 기동은 활성 세대와 그 DB의 결합을 검사하며 운영 쓰기로 바뀐 DB의 과거 내용 해시를 재사용하지 않는다. 중단 시 이전 자료를 보전하고, 공개 차단 상태에서 검증 절차를 재개한다. 운영 배포는 별도 승인이다.

## 복구 검증 흐름

```text
인증된 백업 → 격리 복호화 → 신뢰 기준점부터 삭제 기록 확인
   → 확정 삭제 재적용 → 무결성·조회 검증 → 새 epoch → 공개 재개
누락·미확정·복호화/검증 실패 → 공개 차단 유지 및 운영 결과 기록
```

운영 리허설은 합성 DB의 오래된 사본 생성 후 실제 삭제를 기록하고 그 사본을 복원한다. 정상 복원, 원장 누락, 미확정, 재적용 실패를 독립 실행해 공개 여부를 확인한다. 실제 Raspberry Pi의 부하·자원 성능은 DS-014의 대상 환경에서 확인한다.
