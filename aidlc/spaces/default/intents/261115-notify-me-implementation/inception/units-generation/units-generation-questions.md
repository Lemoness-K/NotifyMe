# Notify Me 구현 작업 단위 분할 초안

## 분할 기준

- 승인된 도메인 컴포넌트와 설계 결정, 요구사항 및 사용자 스토리를 바탕으로 검증 가능한 기능 흐름을 묶는다.
- Raspberry Pi 서버는 모듈형 모놀리스로 유지한다. 공유 웹 UI는 브라우저와 Android 앱에서 사용하고 Android 시스템 기능은 네이티브 어댑터에 둔다.
- 작업 단위는 필요한 구현 의존 관계를 표시한다. 일정과 우선순위는 Delivery Planning에서 정한다.

## 작업 단위와 의존 관계 제안

| ID | 디렉터리 | 종류 | 범위 | 직접 의존 |
|---|---|---|---|---|
| U1 | `u1-core-flow` | service | 로컬에서 초기 가구를 준비하고 인증된 사용자가 공유 웹에서 리마인더를 등록·조회하는 최소 흐름. API와 SQLite 저장까지 실제 경로로 연결한다. | 없음 |
| U2 | `u2-household-and-settings` | service | 초대·역할·가구 접근 회수, 설정 카탈로그와 가구·계정 설정. | U1 |
| U3 | `u3-reminder-workflows` | service | 담당자, 반복·회차, 완료 검증, 목록·이력·보관, 영구 삭제와 서버 변경 기록. | U1, U2 |
| U4 | `u4-android-notifications` | service | Android 앱 셸과 설치별 동기화·예약·권한·시간 및 장소 알림. 같은 서버에 기기 동기화 모듈을 추가한다. | U1, U2, U3 |
| U5 | `u5-operations-and-recovery` | service | 백업·복구, 상태 진단, 선택적 운영 보고와 장애 알림을 실행하는 서버 작업과 Raspberry Pi 실행·업데이트 구성. | U1, U3 |

U1은 독립 실행 가능한 통합 흐름이다. U5는 U3의 변경 기록과 삭제 표지 계약을 사용한다. U4와 U5는 공통 선행 작업이 준비되면 서로의 산출물에 의존하지 않도록 계약을 정한다. 웹 화면 변경은 해당 기능을 구현하는 단위에 포함한다.

## 후속 설계에 전달할 사항

- U3는 여러 서버 변경을 묶을 수 있는 명령 진입점과 검증 경계를 정의한다. U4는 그 경계에 설치 용량 검사와 예약 계획 저장을 연결한다.
- U2는 접근 회수 상태와 신호를 정의하고, U4는 회수 신호와 후속 접근 거부를 받아 해당 기기의 로컬 캐시와 예약을 정리한다.
- U3는 최소 삭제 표지를 제공한다. U5는 복구할 백업보다 최신 표지를 확보해 재적용하고, 검증이 끝난 뒤 데이터 제공을 허용한다.
- 열린 질문은 결정 등록부를 기준으로 추적하고 관련 상세 설계에서 다룬다.
