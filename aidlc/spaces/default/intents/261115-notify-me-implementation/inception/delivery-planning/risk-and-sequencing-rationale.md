## Sources

`requirements.md`, `components.md`, `unit-of-work-dependency.md`, `contract-summary.md`, `team-practices.md`와 확인된 구현·검증 계획에 근거한다.

## 순서의 근거

처음에는 실제 실행 경로를 얇게 연결해 통합 가정을 확인한다. 그 기반 위에 가구·설정과 리마인더 업무를 추가하고, Android에서 핵심 알림 기능을 확인한 뒤 운영과 복구를 검증한다. 정량 우선순위 점수 대신 의존 관계와 해당 단계가 확인할 사용자 가치 및 위험을 사용했다.

U4와 U5는 공통 코드가 있으면 기술적으로 독립 가능하다. 현재는 U3 이후 U4, U5를 순차 실행한다. 사용자 결정에 따라 U3의 완료 조건은 삭제 기록 저장과 실패 처리까지이며 오래된 백업에서의 모의 복원과 전체 복구 검증은 U5에 둔다.

| 위험 | 가능성 / 영향 | 대응과 확인 시점 |
| --- | --- | --- |
| 웹·서버·DB가 권한 경계에서 연결되지 않음 | 중 / 높음 | U1에서 합성 인증을 사용한 실제 저장·재조회 및 거부 확인. 공급자 연동은 비운영 환경에서 분리 확인. |
| 가구 접근이 회수돼도 캐시나 예약이 남음 | 중 / 높음 | U2 회수 상태, U3 업무 정리, U4 기기 정리의 계약과 거부·재연결 흐름을 검증. |
| 삭제 성공 응답 후 복원으로 데이터가 되살아남 | 중 / 높음 | U3에서 확정 저장·실패·재시도 확인. U5에서 격리 복원, 재적용, 누락·미확정 시 재개 차단을 확인. |
| 기기·OS 환경에 따라 알림 동작 차이 | 높음 / 높음 | U4에서 에뮬레이터와 실기기 결과를 분리한다. 권한, 백그라운드, 재부팅과 지오펜스를 확인. |
| Raspberry Pi ARM64 호환성 또는 자원 예산 미달 | 중 / 높음 | 로컬 빌드와 대상 호환성을 구분한다. 대상 성능 측정 전에 하드웨어·부하·메모리·쓰기 예산 조건을 확정. |
| 서로 다른 커버리지 기준으로 검증 결과 혼동 | 높음 / 중 | U1 구현 시작 전 승인된 80% 라인 목표와 이전 테스트 가이드의 표현을 정리하고 실제 명령·결과에 반영. |

열린 제품 정책은 결정 등록부를 계속 사용한다. 테스트가 실행되지 못한 환경에서는 대체 검증이 다룬 범위와 남은 위험을 기록한다.
