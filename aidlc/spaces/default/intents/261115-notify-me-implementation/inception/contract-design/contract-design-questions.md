# Notify Me 계약 설계 초안

## 기준

- 작업 단위 정의와 의존 관계, 도메인 컴포넌트, 요구사항을 바탕으로 각 경계의 제공자, 소비자, 입력·출력, 오류와 재시도 조건을 정한다.
- 서버는 기존 NestJS 모듈형 모놀리스와 SQLite 안에서 실행한다. 같은 서버의 모듈은 타입이 지정된 내부 인터페이스와 필요한 트랜잭션을 공유한다.
- 열린 질문은 결정 등록부를 기준으로 추적하고 관련 상세 설계에서 다룬다.

## 계약 경계 제안

| 경계 | 메커니즘과 책임 |
| --- | --- |
| 브라우저·Android ↔ 공유 서버 | 인증된 HTTPS JSON API. 첫 버전은 `/api/v1`을 제안한다. U1이 인증·공통 오류 규약을 소유하고 가구·설정은 U2, 리마인더·이력은 U3, 설치·동기화는 U4가 소유한다. |
| U1 ↔ Firebase·Google | 외부 신원은 U1의 인증 어댑터가 검증해 내부 User에 연결한다. 가구 인가는 서버가 별도로 처리한다. 실제 공급자 연동 검증은 승인된 비운영 환경을 사용한다. |
| U1·U2·U3 서버 모듈 | 권한·설정 정책, 가구 회수 및 업무 변경을 타입 계약으로 연결한다. 접근 회수와 담당자 정리, 반경 설정과 Trigger 조정은 같은 DB 트랜잭션에 포함한다. |
| U3 ↔ U4, U4 ↔ Android | 설치 용량 확인 및 계획 저장을 서버 변경에 묶는다. FCM 신호는 상태를 다시 가져오라는 안내에 한정하고, 설치는 최신 계획을 가져와 OS 상태를 조정한다. 회수 신호나 후속 가구 접근 거부 시 해당 가구의 로컬 상태를 정리한다. |
| U3 → U5 복구 | 삭제 요청과 확정 기록은 복원 대상 DB와 독립된 경계에 남긴다. U5는 신뢰할 수 있는 백업 기준점과 종료점 사이의 기록을 확인해 삭제를 재적용한다. 누락·미확정·무결성 오류·적용 실패가 있으면 데이터 제공을 차단한다. |
| U1 → U5 운영 | 서버 기동·상태·DB 경계는 로컬 운영 전용으로 제공한다. 관리용 상태와 복구 기능은 공개 API에 포함하지 않는다. |

## 호환성과 실패 처리

- API 오류는 번역 문장 대신 안정된 코드와 구조화된 값을 반환한다. 세션·가구 권한 오류, 입력 오류, 상태 충돌, 설치 용량 초과와 재시도 가능 장애를 구분한다.
- 새 응답 필드는 기존 클라이언트가 무시할 수 있어야 한다. 기존 의미를 바꾸는 변경은 제공자와 소비자가 합의한 새 버전으로 도입한다.
- 변경 명령의 재시도는 작업 키와 상태 확인으로 중복 적용을 막는다. 타임아웃으로 결과를 알 수 없을 때 같은 작업 키로 재시도하며, 이미 거절된 입력은 수정한 뒤 다시 제출한다.

## Consolidated Summary Confirmation

- 웹과 Android는 버전이 있는 HTTPS API로 공유 서버를 사용한다. 서버 모듈은 같은 프로세스 안에서 타입 계약과 필요한 트랜잭션을 사용한다.
- FCM은 갱신 신호를 전달하고 설치는 최신 상태를 가져와 OS 예약과 접근 회수 후 정리를 처리한다.
- 복구는 독립된 삭제 기록의 완전성과 재적용을 확인한 뒤 서비스를 재개한다.
- 경계마다 소유자, 스키마와 오류·재시도·호환성 조건을 명시한다.
