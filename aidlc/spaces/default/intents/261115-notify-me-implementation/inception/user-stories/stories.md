# 사용자 스토리 — Notify Me

## 사용 기준

- **기준 입력:** `requirements` (`../requirements-analysis/requirements.md`). 아래 스토리와 추적성은 이 요구사항 분석을 기준으로 작성한다.
- **계획 요약:** 두 페르소나를 두고 사용자 여정 에픽별로 나눈다. 가구 구성원은 요청자·담당자 맥락과 Admin 역할 변형을 갖고, 운영자는 별도 이해관계자다.
- **우선순위:** 각 `MoSCoW`는 Delivery Planning에 전달하는 우선순위 입력이다. 공식 MVP 경계는 Delivery Planning에서 정한다.
- **ID:** `USg.s`와 `ACg.s.c`는 이 AIDLC 단계의 추적 ID다. 프로젝트 canonical 사용자 이야기 `US-NNN`은 `docs/00-master-design.md`에 그대로 유지한다. 기존 대표 시나리오와의 관계는 해당 스토리에 적는다.
- **수용 기준:** `Given / When / Then`으로 작성했다. 구현 방법이 확정되지 않은 정책은 결과만 기술하고 구체값은 만들지 않는다.
- **열린 범위:** Q-063(완료 검증의 세부 정책)과 Q-064(운영 보고·장애 알림의 세부 정책)은 후속 결정 전까지 열린 상태다. 모든 스토리는 요구사항 분석 및 현재 승인된 제품 결정 안에서 해석한다.

## 에픽 1 — 로그인과 가구 여정

### US1.1 — 인증된 계정으로 접속하기

**스토리:** 가구 구성원으로서, Google 계정으로 로그인하고 현재 설치에서 로그아웃하고 싶다. 내 가구 데이터가 인증된 세션에서만 보이도록 하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** 없음
- **INVEST:** 독립적으로 검증 가능; 로그인 제공자·세션 구현은 협상 가능; 인증된 접근이라는 가치가 분명함; 기술 분해 후 추정; 한 로그인 여정에 한정; 성공·실패·로그아웃을 테스트할 수 있음.
- **AC1.1.1:** Given 지원되는 Google 계정이 있을 때, When 구성원이 로그인하면, Then Firebase Authentication으로 인증되고 업무 데이터는 제공자와 분리된 내부 사용자 ID에 연결된다.
- **AC1.1.2:** Given 유효한 세션이 없거나 만료·취소된 경우, When 구성원이 보호된 사용자·가구 데이터에 접근하면, Then 인증된 접근을 허용하지 않는다.
- **AC1.1.3:** Given 로그인된 설치에서 구성원이 로그아웃할 때, Then 해당 설치의 인증 상태가 종료되고 다시 로그인할 때까지 보호된 데이터 접근이 허용되지 않는다.

### US1.2 — 하나의 가구 공간 사용하기

**스토리:** 가구 구성원으로서, 승인된 단일 가구 공간에 접속하고 싶다. 가구의 공유 업무가 다른 가구의 데이터와 섞이지 않도록 하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US1.1
- **INVEST:** 독립 가치; 가구 선택 UI는 MVP에서 제외; 가구 격리 결과가 명확; 소규모로 추정 가능; 승인된 단일 가구 여정; 접근 격리를 테스트할 수 있음.
- **AC1.2.1:** Given 인증된 사용자가 MVP에 접속할 때, Then 여러 가구 생성·전환 UI 없이 승인된 하나의 가구 공간을 사용한다.
- **AC1.2.2:** Given 다른 household 소유 데이터가 존재할 때, When 현재 가구의 구성원이 데이터를 조회하거나 동기화하면, Then 다른 household의 데이터는 응답·목록·동기화에 포함되지 않는다.

### US1.3 — 최초 Admin 설정하기

**스토리:** 초기 서비스 운영 담당자로서, 검증된 계정에 최초 Admin 가구를 한 번만 초기화하고 싶다. 공개 가입 경로가 가구의 최초 권한을 선점하지 않도록 하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US1.1
- **INVEST:** 독립적인 초기화 결과; 명령·자격 증명 전달 방식은 상세 설계 가능; 안전한 초기화 가치가 분명; 상세 설계 후 추정; 단일 초기화 작업; 반복 호출과 실패를 테스트할 수 있음.
- **AC1.3.1:** Given Household가 아직 초기화되지 않았을 때, When 승인된 서버 bootstrap 절차가 검증된 Google/Firebase 계정을 사용하면, Then Household와 최초 ADMIN Membership가 원자적으로 생성된다.
- **AC1.3.2:** Given 초기화가 이미 완료되었을 때, When bootstrap을 다시 실행하면, Then 새 Household나 계정을 만들지 않고 실패한다.
- **AC1.3.3:** Given 최초 Admin이 아직 없는 상태일 때, When 공개 웹/API 가입 경로를 사용하면, Then 최초 Admin 권한을 생성할 수 없다.

### US1.4 — 이메일 초대로 구성원 가입시키기

**스토리:** Admin으로서, 초대할 이메일에 연결된 가구 가입 링크를 만들고 싶다. 가입자가 의도한 계정과 일치하는지 확인하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US1.3
- **INVEST:** 독립 초대 여정; UI와 토큰 구현은 협상 가능; 검증된 가입 가치가 명확; 보안 설계 후 추정; 발급·수락 흐름에 한정; 이메일 불일치·만료·재사용을 테스트할 수 있음.
- **AC1.4.1:** Given Admin이 초대 이메일을 지정할 때, When 초대를 발급하면, Then 예측 불가능한 링크를 공유할 수 있고 초대는 24시간 만료·일회용·취소 가능하다.
- **AC1.4.2:** Given 유효한 초대 링크를 연 경우, When 링크를 조회(GET)하기만 하면, Then 초대는 소비되지 않고 Membership도 생성되지 않는다.
- **AC1.4.3:** Given 초대를 수락하는 계정이 있을 때, When 인증된 Google 이메일이 초대 대상과 일치하고 검증 완료되면, Then 사용자는 MEMBER로 추가된다; 불일치하면 초대가 소비되지 않는다.
- **AC1.4.4:** Given 초대 수락이 끝났을 때, Then 외부 인증 신원은 내부 사용자 ID에 연결되고 가구 권한은 인증 제공자 claim만으로 부여되지 않는다.

### US1.5 — 가구 역할과 Admin 유지 관리하기

**스토리:** Admin으로서, 구성원의 역할을 관리하고 싶다. 가구 설정을 담당하면서 항상 최소 한 명의 Admin이 남도록 하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US1.4
- **INVEST:** 독립적인 권한 관리 결과; 화면 배치는 협상 가능; 역할 관리와 가용성이 명확; 트랜잭션 설계 후 추정; 한 가구의 역할 정책; 마지막 Admin 경계를 테스트할 수 있음.
- **AC1.5.1:** Given 활성 가구의 구성원이 있을 때, When Admin이 MEMBER/ADMIN 역할이나 가구 설정을 변경하면, Then 승인된 역할 권한에 따라 변경된다.
- **AC1.5.2:** Given 가구에 Admin이 한 명만 있을 때, When 다른 Admin으로의 인계 없이 그 Admin을 강등하거나 제거하려고 하면, Then 변경은 거부된다.
- **AC1.5.3:** Given 기존 Admin을 내보내거나 강등하려는 요청에 활성 Member 대상이 포함될 때, Then Admin 인계와 해당 변경이 원자적으로 처리되어 Admin이 한 명 이상 유지된다.

### US1.6 — 가구의 Reminder를 공동 관리하기

**스토리:** 가구 구성원으로서, 권한 매트릭스에 따라 가구 Reminder를 함께 조회하고 관리하고 싶다. 부탁을 다른 사람에게 맡기더라도 모두가 현재 상태를 공유하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US1.2
- **INVEST:** 독립 가치; 세부 API 경계는 협상 가능; 공유된 현재 상태가 명확; 대표 CRUD 흐름으로 추정; 한 가구 업무에 한정; Member/Admin 권한 및 household 격리를 테스트 가능.
- **AC1.6.1:** Given 가구의 유효한 구성원일 때, When 구성원이 Reminder를 조회·생성·수정·삭제·완료·완료 취소하면, Then 기존 권한 매트릭스와 검증 설정 여부를 따른다.
- **AC1.6.2:** Given 해당 가구에 속하지 않은 인증 사용자가 있을 때, When 동일한 Reminder ID로 요청하면, Then 읽기와 변경이 모두 허용되지 않는다.

### US1.7 — 구성원 제거 후 접근과 이력 정리하기

**스토리:** Admin으로서, 가구에서 구성원을 제거하고 싶다. 그 구성원의 접근과 배정은 끝내되 기존 업무 이력은 보존하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US1.5
- **INVEST:** 독립적인 구성원 변경 결과; 클라이언트 정리 프로토콜은 협상 가능; 접근 회수와 기록 보존이 명확; 상세 설계 후 추정; 제거 동작에 한정; 활성·오프라인 설치 상태를 테스트할 수 있음.
- **AC1.7.1:** Given Admin이 구성원을 제거할 때, When 변경이 적용되면, Then Membership 접근 권한과 해당 구성원의 활성 Assignment·알림 대상이 제거되고 Reminder·Occurrence·완료·변경 이력은 보존된다.
- **AC1.7.2:** Given 제거되는 사람이 미완료 Reminder의 마지막 담당자일 때, Then 미완료 회차는 PENDING·무담당 상태로 남는다.
- **AC1.7.3:** Given 제거된 사용자의 설치가 권한 회수 신호를 받거나 이후 API 거부를 확인할 때, Then household 캐시, 로컬 알림 예약과 geofence를 정리한다; force-stop 상태에서 신호 전달 자체는 보장하지 않는다.

## 에픽 2 — Reminder 생성·수정·완료 여정

### US2.1 — 새 부탁 등록하기

**스토리:** 요청자로서, 제목과 필요 정보를 담은 Reminder를 등록하고 싶다. 부탁을 기억에서 공유 가능한 할 일로 옮기기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US1.6
- **INVEST:** 독립적인 생성 결과; 편집 UI는 협상 가능; 기억 부담을 줄이는 가치가 분명; 기본 필드로 추정 가능; 한 Reminder 생성; 필수값·기본값을 테스트할 수 있음.
- **프로젝트 대표 시나리오:** `docs/00-master-design.md`의 `US-001`과 연결.
- **AC2.1.1:** Given 가구 구성원이 유효한 필수 제목을 입력할 때, When Reminder를 저장하면, Then Reminder가 공유 가구에 생성되고 작성자와 요청자 정보가 보존된다.
- **AC2.1.2:** Given 선택 설명이 입력되었을 때, Then 제목·설명은 작성자가 입력한 원문으로 보존되고 기존 승인된 유효성·기본값 규칙을 따른다.
- **AC2.1.3:** Given 필수 입력이 유효하지 않을 때, When 저장하면, Then 유효하지 않은 Reminder를 생성하지 않고 수정할 수 있는 입력을 유지한다.

### US2.2 — 요청자와 담당자를 구분하기

**스토리:** 요청자 또는 Admin으로서, Reminder에 한 명 이상의 가구 담당자를 지정하고 싶다. 누가 부탁했고 누가 수행할지 서로 알기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US2.1
- **INVEST:** 생성 흐름 안에서 독립 검증; 할당 UI 방식은 협상 가능; 책임 공유가 명확; 추정 가능; 담당자 지정 단위; 요청자·담당자 관계를 테스트할 수 있음.
- **프로젝트 대표 시나리오:** `US-002`의 다른 구성원에게 부탁하는 흐름과 연결.
- **AC2.2.1:** Given Reminder 작성자가 요청자와 담당자를 지정하거나 기존 기본값을 사용할 때, Then 요청자(`requester_user_id`)와 실제 수행자를 별도 정보로 저장한다.
- **AC2.2.2:** Given 여러 가구 구성원이 담당자로 지정될 때, Then Reminder는 모든 승인된 담당자를 대상으로 하고 담당 설치를 알림 대상 계산에 사용한다.
- **AC2.2.3:** Given 사용자 설정과 담당자가 변경될 때, Then 감사 이력에는 변경 행위자와 변경 내용을 남긴다.

### US2.3 — 공유 Reminder 조회하고 수정하기

**스토리:** 가구 구성원으로서, 현재 Reminder의 내용과 담당자를 보고 권한에 따라 수정하고 싶다. 부탁 내용이 바뀌어도 모두가 최신 상태를 보도록 하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US2.1
- **INVEST:** 독립적인 변경 결과; 상세 편집 구성은 협상 가능; 정합성 가치가 분명; 작은 CRUD 단위; 한 Reminder 변경; 권한·이력·동기화를 테스트할 수 있음.
- **프로젝트 대표 시나리오:** `US-006`의 내용·담당자·일정 수정 흐름과 연결.
- **AC2.3.1:** Given 가구 구성원이 권한 있는 Reminder를 열었을 때, Then 현재 내용, 요청자·담당자, 반복·Trigger 및 상태를 확인한다.
- **AC2.3.2:** Given 구성원이 Reminder를 수정하면, Then 공유 데이터가 갱신되고 변경 행위자와 주요 변경 이력이 보존된다.
- **AC2.3.3:** Given 권한이 없는 사용자가 변경을 시도할 때, Then 변경은 거부되고 기존 데이터는 보존된다.

### US2.4 — 검증 없는 회차 완료하기

**스토리:** 가구 구성원으로서, 검증이 꺼진 Reminder의 회차를 완료 표시하고 싶다. 완료 상태를 가구에 공유하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US2.1
- **INVEST:** 독립적인 상태 변경; 버튼 형태는 협상 가능; 수행 완료 공유 가치가 분명; 소규모; 한 회차 완료; 반복·이력 경계를 테스트 가능.
- **프로젝트 대표 시나리오:** `US-003`과 연결.
- **AC2.4.1:** Given 검증이 꺼진 활성 회차일 때, When 가구 구성원이 완료하면, Then 회차가 완료 상태로 바뀌고 수행자·완료 시각이 기록된다.
- **AC2.4.2:** Given 한 Reminder에 여러 담당자가 있을 때, When 기존 결정에 따라 회차 완료 처리가 적용되면, Then 해당 회차의 완료 결과가 담당자에게 일관되게 공유된다.
- **AC2.4.3:** Given 완료 변경이 저장되면, Then 다른 연결 클라이언트에서도 해당 회차와 활동 이력을 같은 상태로 조회한다.

### US2.5 — 검증 없는 완료를 취소하기

**스토리:** 가구 구성원으로서, 검증이 꺼진 회차의 완료 표시를 되돌리고 싶다. 잘못 완료했거나 다시 수행해야 하는 일을 활성 목록으로 돌리기 위해서다.

- **MoSCoW:** Should Have (계획 입력)
- **선행:** US2.4
- **INVEST:** 독립 결과; 취소 UI는 협상 가능; 오류 복구 가치가 명확; 소규모; 단일 회차; 상태와 감사 이력을 테스트 가능.
- **AC2.5.1:** Given 검증이 꺼진 완료 회차가 있을 때, When 가구 구성원이 완료 취소를 실행하면, Then 승인된 기존 정책에 따라 회차가 미완료 상태로 복귀한다.
- **AC2.5.2:** Given 완료를 취소했을 때, Then 취소 행위자와 시각이 기록되고 연결 클라이언트가 새 상태를 확인한다.
- **AC2.5.3:** Given 검증 대기 또는 검증 완료 회차일 때, When 이 스토리의 검증 없는 완료 취소 흐름을 요청하면, Then Q-063에서 미결정인 상호작용을 임의로 적용하지 않는다.

### US2.6 — Reminder 보관하고 복원하기

**스토리:** 가구 구성원으로서, 당장 보이지 않아도 될 Reminder를 보관하고 나중에 복원하고 싶다. 설정·이력을 유지하면서 활성 목록과 반복 생성을 정리하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US2.1
- **INVEST:** 독립적인 수명주기 변경; 보관함 화면은 협상 가능; 숨김과 복귀 가치가 명확; 제한된 상태 변경; 한 Reminder; 반복·예약 부작용을 테스트할 수 있음.
- **AC2.6.1:** Given 활성 Reminder가 있을 때, When 가구 구성원이 보관하면, Then 활성 목록에서 빠지고 설정·이력은 유지되며 새 알림·반복 회차 생성이 중지된다.
- **AC2.6.2:** Given 보관된 Reminder가 있을 때, When 구성원이 보관함에서 복원하면, Then Reminder를 조회할 수 있고 반복은 원래 규칙의 다음 미래 회차부터 재개된다.
- **AC2.6.3:** Given 보관 전에 만들어진 PENDING 회차가 있을 때, Then 복원 후 기존 회차가 다시 활성화되고 시간이 지난 TIME 회차는 OVERDUE로 표시하며 과거 알림을 재생하지 않는다.
- **AC2.6.4:** Given 보관 Reminder에 LOCATION Trigger가 있을 때, Then 복원 후 해당 Trigger를 다시 등록하고 보관 기간 동안 지나간 반복 회차를 생성하거나 MISSED로 남기지 않는다.

### US2.7 — Reminder를 영구 삭제하기

**스토리:** 가구 구성원으로서, 더 이상 필요 없는 Reminder를 되돌릴 수 없음을 확인한 뒤 영구 삭제하고 싶다. 앱의 업무 데이터와 이력을 명시적으로 제거하기 위해서다.

- **MoSCoW:** Should Have (계획 입력)
- **선행:** US2.1
- **INVEST:** 독립적인 명시 삭제 여정; 확인 UI는 협상 가능; 사용자가 통제하는 삭제 가치; 구현상 주의 필요; 한 Reminder의 파괴적 변경; 백업·동기화 경계를 테스트할 수 있음.
- **AC2.7.1:** Given 활성 또는 보관 Reminder에서 영구 삭제를 시작할 때, Then 확인 화면에 대상 제목과 앱에서 복구할 수 없다는 내용을 표시한다.
- **AC2.7.2:** Given 사용자가 확인 화면에서 영구 삭제를 명시적으로 다시 선택할 때만, Then Reminder와 연결 회차 이력이 앱과 운영 DB에서 제거되고 다른 가구 데이터는 보존된다.
- **AC2.7.3:** Given 다른 설치나 백업에 삭제 전 데이터가 남아 있을 때, Then 동기화 tombstone과 암호화 복구 백업은 승인된 최대 30일 정책을 따르고 복구 전 삭제를 재적용한다.

## 에픽 3 — 반복 규칙과 회차 여정

### US3.1 — 반복 Reminder 설정하기

**스토리:** 요청자로서, Reminder를 매일·매주·매월 반복하고 선택 종료일을 지정하고 싶다. 반복 부탁을 매번 다시 입력하지 않기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US2.1
- **INVEST:** 독립적인 반복 설정; 날짜 입력 방식은 협상 가능; 반복 업무 자동화 가치; 규칙별 추정; 일·주·월과 종료일 범위; 시간대·월말 경계를 테스트할 수 있음.
- **프로젝트 대표 시나리오:** `US-004`의 주간 반복 사례와 연결.
- **AC3.1.1:** Given Reminder를 생성하거나 수정할 때, When 일·주·월 반복 및 선택 종료일을 저장하면, Then RecurrenceRule이 선택한 빈도와 기준 시간대를 보존한다.
- **AC3.1.2:** Given 주간 요일·반복 간격 또는 월간 날짜 규칙이 선택될 때, Then 첫 주의 시작일, 설정된 주간 convention, 월말 및 시간대 경계는 승인된 기존 결정대로 다음 회차를 계산한다.
- **AC3.1.3:** Given 같은 규칙의 생성 작업이 재시도될 때, Then 같은 회차를 중복 생성하지 않는다.

### US3.2 — 반복 규칙의 적용 범위를 골라 수정하기

**스토리:** 요청자로서, 반복 Reminder를 수정할 때 이번 회차와 이후 회차 또는 전체 반복 중 적용 범위를 고르고 싶다. 이미 정한 회차와 앞으로의 약속을 구분하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US3.1
- **INVEST:** 독립적인 편집 결과; 선택 UI는 협상 가능; 기존·미래 일정 보호 가치; 상세 규칙 후 추정; 세 가지 승인 범위; 전·후 회차를 테스트 가능.
- **AC3.2.1:** Given 반복 Reminder의 내용을 수정할 때, When 사용자가 이번 회차와 이후 회차 또는 전체 반복 중 범위를 선택하면, Then 변경은 승인된 범위에만 적용된다.
- **AC3.2.2:** Given 범위 수정이 저장되면, Then 이미 완료·취소된 이력과 범위 밖 회차는 유지된다.

### US3.3 — 반복 회차와 Reminder 수명주기 구분하기

**스토리:** 가구 구성원으로서, 반복 Reminder의 개별 회차 상태와 Reminder 자체의 활성·보관 상태를 구분해 보고 싶다. 일정 반복과 개별 수행 이력을 혼동하지 않기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US3.1
- **INVEST:** 독립적인 상태 이해 결과; 시각화 방식은 협상 가능; 정확한 상태 인식 가치; 검증 가능한 전이; 상태 경계 한 영역; 시간 경계별 테스트 가능.
- **AC3.3.1:** Given Reminder와 Occurrence가 존재할 때, Then Reminder의 활성·보관 수명주기와 Occurrence의 진행 상태를 별도 값으로 관리한다.
- **AC3.3.2:** Given 반복 Reminder의 다음 예정 시각이 도달하고 이전 회차가 PENDING일 때, Then 이전 회차를 MISSED로 보존하고 새 회차는 원래 규칙에 따라 유지한다.
- **AC3.3.3:** Given 단발 회차가 미완료일 때, Then 시간 경과나 장소 알림만으로 닫지 않고 활성 할 일로 유지하며 시간 Trigger 회차는 OVERDUE로 구분한다.

### US3.4 — 담당자가 없는 반복을 일시 중지하기

**스토리:** 가구 구성원으로서, 반복 Reminder의 담당자가 없을 때 새 회차 생성을 멈추고 담당자가 다시 지정되면 계속 이어가고 싶다. 아무도 맡지 않은 반복 할 일이 쌓이지 않도록 하기 위해서다.

- **MoSCoW:** Should Have (계획 입력)
- **선행:** US3.1, US2.2
- **INVEST:** 독립적인 일시 중지 동작; 상태 표시는 협상 가능; 무담당 회차 방지 가치; 제한된 전이; 반복 Reminder의 담당자 경계; 담당자 재지정 시나리오를 테스트 가능.
- **AC3.4.1:** Given 담당자가 없는 반복 Reminder일 때, Then 새 Occurrence 생성이 일시 중지된다.
- **AC3.4.2:** Given 반복 Reminder에 담당자가 다시 지정될 때, Then 생성이 재개되며 같은 회차를 중복 생성하지 않는다.

### US3.5 — 현재 반복 회차 하나 건너뛰기

**스토리:** 가구 구성원으로서, 반복 규칙은 유지한 채 현재 PENDING 회차 하나만 건너뛰고 싶다. 이번 일정만 수행하지 않고 다음 반복은 계속하기 위해서다.

- **MoSCoW:** Should Have (계획 입력)
- **선행:** US3.1
- **INVEST:** 독립적인 회차 상태 변경; 액션 위치는 협상 가능; 반복 규칙 보존 가치; 한 회차만 변경; 이력과 설치 예약을 테스트할 수 있음.
- **AC3.5.1:** Given 반복 Reminder의 현재 회차가 PENDING일 때, When 가구 구성원이 건너뛰면, Then 해당 회차만 SKIPPED가 되고 RecurrenceRule과 다른 회차는 바뀌지 않는다.
- **AC3.5.2:** Given 회차를 건너뛰면, Then 행위자·시각을 이력에 남기고 담당자 설치의 해당 회차 알림·geofence 예약을 취소한다.

## 에픽 4 — 시간·장소 알림과 기기 동기화 여정

### US4.1 — 시간 Trigger 알림 받기

**스토리:** 담당자로서, Reminder의 예정 시각에 Android 시스템 알림을 받고 싶다. 앱을 계속 열어두지 않아도 할 일을 기억하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US2.2
- **INVEST:** 독립적인 시간 알림 흐름; 예약 구현은 협상 가능; 적시 수행 가치; Android 상세 설계 후 추정; 시간 Trigger 하나; 권한·재부팅·중복 사례를 테스트할 수 있음.
- **AC4.1.1:** Given 시간 Trigger가 저장되어 있고 대상 설치 권한이 허용될 때, When 예정 시각이 오면, Then 해당 설치에 Android 로컬 알림을 게시한다.
- **AC4.1.2:** Given 앱 프로세스가 종료되거나 기기가 재부팅된 뒤일 때, Then 유효한 저장 일정은 복구되고 이미 취소·완료된 예약은 다시 게시되지 않는다.
- **AC4.1.3:** Given 정확 알람 권한이나 OS 정책으로 정확 시각 실행이 보장되지 않을 때, Then 기존 승인된 지연 허용·권한 안내 정책을 따른다.

### US4.2 — 장소 조건에 맞는 알림 받기

**스토리:** 담당자로서, 장소와 선택한 진입·이탈·머무름 조건을 Reminder에 지정하고 조건이 발생하면 알림을 받고 싶다. 위치에 도착하거나 떠날 때 필요한 일을 떠올리기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US2.2
- **INVEST:** 독립적인 장소 Trigger; 플랫폼 구현은 협상 가능; 맥락 기반 알림 가치가 명확; 경계 조건 설계 후 추정; Android 장소 조건; 반경·이벤트·권한 경계를 테스트 가능.
- **AC4.2.1:** Given LOCATION Trigger를 설정할 때, When 장소·반경·진입/이탈/머무름/이탈 후 경과 중 하나의 이벤트를 저장하면, Then 선택한 조건으로 대상 Android 설치에서 감시한다.
- **AC4.2.2:** Given Reminder에 Trigger를 저장할 때, Then TIME과 LOCATION은 동시에 지정할 수 없고 LOCATION에는 이벤트 유형 하나만 저장한다.
- **AC4.2.3:** Given LOCATION Trigger의 기본 반경을 보여줄 때, Then 초기 100m를 표시하고 현재 가구의 최소·최대 경계 안에서 25m 단위 조정을 제공한다.
- **AC4.2.4:** Given DWELL 또는 AFTER_EXIT 지속 시간이 직접 입력될 때, Then 1분부터 가구 설정 상한까지 정수 분으로 검증한다.

### US4.3 — 기기 권한 상태 확인하고 복구하기

**스토리:** 가구 구성원으로서, 설치의 알림·위치 권한 상태와 사용 불가 기능을 확인하고 OS 설정으로 이동하고 싶다. 권한이 없어도 기본 업무를 계속 관리하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US4.1
- **INVEST:** 독립적인 권한 안내 결과; 화면은 협상 가능; 실패 원인과 복구 경로가 명확; 소규모; 설치 단위 상태; 허용·거부 흐름을 테스트할 수 있음.
- **AC4.3.1:** Given 설치에서 알림 또는 위치 권한이 거부될 때, Then 해당 설치의 알림 상태와 제한을 표시하되 Reminder 생성·조회 등 기본 업무 관리 기능은 허용한다.
- **AC4.3.2:** Given LOCATION Reminder를 저장할 때 위치 권한이 거부되어 있으면, Then 저장을 허용하고 그 설치에서 알림이 불가하다는 상태와 복구 경로를 보여준다.
- **AC4.3.3:** Given Android 권한이나 알림 채널 설정을 바꾸려는 사용자가 있을 때, Then 해당 Android OS 설정 화면으로 이동할 수 있다.

### US4.4 — 담당 설치로 안전한 알림 전달하기

**스토리:** 가구 구성원으로서, 내게 지정된 Reminder 알림을 받고 민감한 내용이 잠금 화면에 과하게 노출되지 않도록 하고 싶다. 다른 사람의 설치에 내 담당 알림이 가거나 비공개 정보가 노출되지 않게 하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US2.2, US4.1
- **INVEST:** 독립적인 전달 대상·표시 결과; Android 채널 세부는 협상 가능; 개인정보와 적절한 수신의 가치; 알림 설계 후 추정; 설치 대상 하나; 담당 변경·잠금 화면을 테스트할 수 있음.
- **AC4.4.1:** Given Reminder의 담당자들이 정해져 있을 때, Then 시간·장소 알림 대상은 해당 담당자에게 연결된 설치로 제한한다.
- **AC4.4.2:** Given Android 알림이 게시될 때, Then 시간 알림과 장소 알림은 서로 다른 OS 채널을 사용하고 최종 소리·표시·방해 금지는 설치 OS 설정에 따른다.
- **AC4.4.3:** Given 알림이 잠금 화면에 표시될 때, Then Android private visibility와 일반 publicVersion으로 승인된 개인정보 공개 정책을 따른다.

### US4.5 — 지오펜스 용량 초과를 막고 입력 보존하기

**스토리:** Reminder 작성자 또는 Admin으로서, 새 장소 알림이나 담당자 변경이 설치의 geofence 용량을 초과하면 저장 전에 알려주고 싶다. 일부 설치에서만 조용히 알림이 빠지는 것을 방지하기 위해서다.

- **MoSCoW:** Should Have (계획 입력)
- **선행:** US2.2, US4.2
- **INVEST:** 독립적인 용량 보호 흐름; 슬롯 확보 UI는 협상 가능; 데이터·알림 일관성 가치; 플랫폼 상세 설계 후 추정; 저장 시 한도 검사; 거부·재시도와 기존 항목 제거를 테스트 가능.
- **AC4.5.1:** Given 새 LOCATION Reminder나 담당자 변경으로 대상 설치 중 하나의 geofence 한도를 넘을 때, When 저장하면, Then 전체 변경을 저장하지 않고 사용자 입력을 보존하며 용량이 찬 설치를 알린다.
- **AC4.5.2:** Given 사용자가 해당 설치에서 기존 geofence를 제거하려고 할 때, Then 영향받을 Reminder·설치와 그 설치의 장소 감지가 중지된다는 점을 알리고 확인을 받는다.
- **AC4.5.3:** Given 용량을 확보한 뒤 사용자가 다시 시도할 때, Then 입력을 다시 제출할 수 있고 관련 설치의 상태를 감시 중지/활성으로 표시한다; 다른 설치와 가구 데이터는 유지한다.

### US4.6 — 웹과 Android에서 공유 상태 확인하기

**스토리:** 가구 구성원으로서, 브라우저와 Android 앱에서 같은 핵심 Reminder 흐름과 최신 공유 상태를 사용하고 싶다. 사용하는 기기가 달라도 부탁을 이어가기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US1.6
- **INVEST:** 독립적인 멀티클라이언트 결과; 동기화 구현은 협상 가능; 연속 사용 가치; API 설계 후 추정; 웹·Android 공통 도메인 흐름; 웹 기능 경계와 동기화를 테스트할 수 있음.
- **AC4.6.1:** Given 브라우저나 Android가 연결되어 있을 때, Then HTTPS를 통해 서버의 공유 Reminder를 조회·변경한다.
- **AC4.6.2:** Given 한 클라이언트의 Reminder 변경이 저장될 때, Then 다른 클라이언트는 최신 공유 상태를 조회할 수 있다.
- **AC4.6.3:** Given FCM 변경 신호를 받을 때, Then 이를 동기화 트리거로 사용하고 사용자에게 보이는 알림으로 취급하지 않는다.
- **AC4.6.4:** Given 브라우저에 Android OS 전용 알림·geofence 기능이 없을 때, Then 공유 웹 UI에서 해당 기능이 지원되지 않음을 안내한다.

### US4.7 — 기기 상태 변화 뒤 로컬 예약 맞추기

**스토리:** 담당자로서, 앱 재시작·재부팅·권한·시간대 변경 뒤 로컬 알림과 geofence가 서버 상태에 맞춰 복구되길 원한다. 오래되거나 중복된 설치 예약을 피하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US4.1, US4.2, US4.6
- **INVEST:** 독립적인 설치 복구 결과; reconcile 구현은 협상 가능; 신뢰성 가치; 이벤트 조합으로 추정; 설치 단위 복구; 재실행·재부팅·시계 변경을 테스트할 수 있음.
- **AC4.7.1:** Given 앱 재시작, 재부팅, 권한 변경, 기기 시간대 또는 시계 변경이 발생할 때, Then 설치별 예약과 geofence를 서버의 현재 Reminder·회차 상태에 맞춰 reconcile한다.
- **AC4.7.2:** Given reconcile 작업이 재시도되거나 중복 실행될 때, Then 로컬 예약을 중복 생성하지 않고 취소된 예약을 남기지 않는다.
- **AC4.7.3:** Given DST 또는 기기 시계 변화가 있을 때, Then 저장된 Occurrence와 RecurrenceRule은 이동·중복 생성하지 않고 OS 예약만 승인된 시간 규칙에 맞춰 조정한다.

## 에픽 5 — 목록·이력·반응형 탐색 여정

### US5.1 — 내 할 일 보기

**스토리:** 담당자로서, 내 활성 할 일을 기한 초과·오늘·예정 상태로 구분해 보고 싶다. 먼저 처리해야 할 일을 빠르게 찾기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US2.2
- **INVEST:** 독립적인 목록 결과; 시각적 배치는 협상 가능; 실행 우선순위 가치; 기본 필터로 추정; 활성 담당 항목; 분류·정렬을 테스트 가능.
- **AC5.1.1:** Given 현재 사용자에게 활성 미완료 Occurrence가 있을 때, Then `내 할 일` 보기는 해당 담당 항목을 기존 기한 초과·오늘·예정 분류와 승인된 정렬로 표시한다.
- **AC5.1.2:** Given 사용자가 앱을 처음 열 때, Then 기본 보기는 `내 할 일`이다.

### US5.2 — 내가 요청한 일 보기

**스토리:** 요청자로서, 내가 요청한 활성 미완료 일을 담당자와 무관하게 보고 싶다. 부탁이 수행되고 있는지 따라가기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US2.1
- **INVEST:** 독립적인 요청자 목록; 선택 UI는 협상 가능; 요청 추적 가치; 기존 분류를 재사용; requester 기준 목록; 사용자가 생성한 것과 요청한 것을 구분해 테스트 가능.
- **프로젝트 대표 시나리오:** `US-002`의 부탁 추적과 연관.
- **AC5.2.1:** Given 활성·미완료 Occurrence의 `requester_user_id`가 현재 사용자일 때, Then `내가 요청한 일` 보기에 포함한다.
- **AC5.2.2:** Given 사용자가 만든 사람과 요청자가 다를 때, Then `created_by`가 아니라 `requester_user_id`를 기준으로 포함 여부를 결정한다.
- **AC5.2.3:** Given 항목이 완료·놓침·건너뜀 상태이거나 보관 Reminder일 때, Then 이 활성 요청 목록에 포함하지 않는다.

### US5.3 — 가구 전체 할 일 보기

**스토리:** 가구 구성원으로서, 가구의 활성 업무를 한 목록에서 보고 싶다. 누가 담당하는지와 상관없이 가구의 현재 상태를 확인하기 위해서다.

- **MoSCoW:** Should Have (계획 입력)
- **선행:** US1.6
- **INVEST:** 독립적인 공유 목록; 화면 밀도는 협상 가능; 전체 업무 인식 가치; 기존 분류를 재사용; 활성 가구 항목; 격리와 상태를 테스트 가능.
- **AC5.3.1:** Given 활성 가구 Reminder가 있을 때, Then 승인된 `가구 전체` 보기에서 담당 여부와 무관하게 가구 권한 범위의 활성 미완료 항목을 볼 수 있다.
- **AC5.3.2:** Given 한 가구의 전체 목록을 조회할 때, Then 다른 household 자료를 포함하지 않고 기한 초과·오늘·예정 분류를 재사용한다.

### US5.4 — 완료·변경 이력 확인하기

**스토리:** 가구 구성원으로서, 완료·놓침·건너뜀과 주요 변경의 행위자·시각을 확인하고 싶다. 무엇이 언제 바뀌었는지 서로 이해하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US2.4
- **INVEST:** 독립적인 이력 열람 결과; 타임라인 UI는 협상 가능; 책임과 회고 가치; 기존 이력 모델 활용; 한 Reminder 또는 승인된 가구 범위; 상태 전이와 행위자를 테스트할 수 있음.
- **프로젝트 대표 시나리오:** `US-005`와 연결.
- **AC5.4.1:** Given 완료·놓침·건너뜀 또는 주요 변경이 발생할 때, Then 발생한 회차, 행위자와 시각을 이력에 보존한다.
- **AC5.4.2:** Given 구성원이 Reminder별 또는 승인된 가구 전체 범위 이력을 열 때, Then Reminder 수명주기와 Occurrence 진행 상태를 구분해 보여준다.
- **AC5.4.3:** Given 사용자가 이력 화면에서 상태 흐름을 확인할 때, Then 승인된 고정 상태 흐름에서 현재 상태를 구분하고 전이 규칙 편집은 제공하지 않는다.

### US5.5 — 보관함 탐색하기

**스토리:** 가구 구성원으로서, 최근 보관된 Reminder를 찾아 복원하거나 영구 삭제하고 싶다. 활성 목록을 복잡하게 만들지 않고 과거에 보관한 일을 다시 관리하기 위해서다.

- **MoSCoW:** Should Have (계획 입력)
- **선행:** US2.6
- **INVEST:** 독립적인 보관함 탐색; 화면 배치는 협상 가능; 보관 데이터 접근 가치; 기존 목록 재사용; 보관 목록·최근순 정렬; 조회·복원·삭제를 테스트 가능.
- **AC5.5.1:** Given 보관된 Reminder가 있을 때, Then 구성원은 보관함에서 조회할 수 있고 목록은 승인된 최근 보관순으로 정렬된다.
- **AC5.5.2:** Given 보관함에서 Reminder를 선택할 때, Then 권한에 따라 상세 조회·복원·영구 삭제로 이동할 수 있고 보관 이력과 설정을 확인할 수 있다.

### US5.6 — 다양한 뷰포트와 입력 방식으로 사용하기

**스토리:** 가구 구성원으로서, 기기 너비에 따라 재배치되는 공유 UI를 키보드나 터치로 사용하고 싶다. 특정 화면 크기에 묶이지 않고 핵심 흐름을 완료하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US5.1
- **INVEST:** 독립적인 접근·사용 결과; breakpoint·레이아웃은 설계 가능; 다양한 기기 지원 가치; 화면별 분해 가능; 공통 흐름에 적용; 뷰포트·키보드·터치를 테스트 가능.
- **AC5.6.1:** Given 가용 웹 뷰포트가 달라질 때, Then UI는 고정 기기 폭이나 최소 화면 크기 가정 없이 내용을 유동적으로 재배치하고 가로 넘침을 만들지 않는다.
- **AC5.6.2:** Given 대표 테스트 폭을 검증할 때, Then 해당 값은 테스트 샘플일 뿐 최소 지원 폭으로 해석되지 않는다.
- **AC5.6.3:** Given 핵심 흐름을 사용할 때, Then 키보드와 터치로 조작 가능하고 상태 선택을 색상만으로 구분하지 않는다.
- **AC5.6.4:** Given 공유 UI가 Android의 네이티브 권한·알림·geofence 기능과 만날 때, Then 도메인·공유 UI는 Android 전용 기능에 직접 의존하지 않고 플랫폼 기능 경계를 통해 안내한다.

## 에픽 6 — 설정과 다국어 여정

### US6.1 — 설정의 소유 범위 확인하기

**스토리:** 가구 구성원으로서, 가구·개인·설치·Reminder 설정이 각각 누구에게 속하는지 알고 올바른 위치에서 관리하고 싶다. 기기 전용 상태가 계정 설정으로 오해되거나 공유 설정이 사라지는 일을 막기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US1.6
- **INVEST:** 독립적인 설정 모델 사용 결과; 실제 편집 화면은 협상 가능; 값 소유권의 명확성이 중요; 상세 설정 설계 후 추정; 네 가지 scope; scope별 조회·공유를 테스트 가능.
- **AC6.1.1:** Given 설정을 조회하거나 바꿀 때, Then Household·User·Installation·Reminder 중 승인된 정확히 하나의 소유 범위를 따른다.
- **AC6.1.2:** Given USER 설정을 저장할 때, Then `user_id`에 귀속되어 같은 사용자의 다른 설치에서 읽는다.
- **AC6.1.3:** Given OS가 소유한 INSTALLATION 설정을 사용할 때, Then 계정·가구 값으로 복제하지 않고 기기 상태로 관리한다.
- **AC6.1.4:** Given REMINDER 설정을 저장할 때, Then 해당 Reminder·Trigger·RecurrenceRule에 보존한다.

### US6.2 — 계정 언어를 선택하고 다른 설치와 공유하기

**스토리:** 가구 구성원으로서, 개인 설정에서 UI 언어를 한국어 또는 영어로 선택하고 싶다. 같은 계정의 다른 설치에서도 익숙한 언어를 사용하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US1.1
- **INVEST:** 독립적인 언어 선택 결과; 선택 UI는 협상 가능; 접근성·개인 선호 가치; 두 locale 범위; 계정 동기화와 fallback을 테스트 가능.
- **AC6.2.1:** Given 사용자가 언어를 선택할 때, Then 선택값을 User scope에 저장하고 `ko-KR` 또는 `en-US`를 지원한다.
- **AC6.2.2:** Given 저장된 지원 사용자 locale이 있을 때, Then 다른 설치도 저장값을 우선 사용한다.
- **AC6.2.3:** Given 저장값이 없거나 유효하지 않을 때, Then 지원되는 기기 locale을 사용하고 기기 locale도 지원되지 않으면 `ko-KR`로 표시한다.

### US6.7 — 장소 Trigger 지속 시간 상한 관리하기

## 에픽 7 — 선택적 완료 검증 여정

### US7.1 — Reminder별 완료 검증 켜기

**스토리:** Reminder 요청자로서, 특정 Reminder에 선택적 완료 검증을 켜고 다른 가구 구성원을 검증자로 지정하고 싶다. 중요한 부탁의 완료를 별도 확인하기 위해서다.

- **선행:** US2.1
- **INVEST:** 독립적인 선택 기능 설정; 나머지 verifier 정책은 협상·결정 필요; 신뢰할 수 있는 완료 확인 가치; Q-063 후 추정; Reminder별 설정; on/off와 다른 구성원 지정만 검증하고 미결정 상호작용은 제외.
- **AC7.1.1:** Given Reminder 작성·수정 시 완료 검증을 선택할 수 있을 때, Then 검증은 해당 Reminder에만 적용된다.
- **AC7.1.2:** Given 완료 검증을 켤 때, Then 다른 가구 구성원을 검증자로 선택할 수 있고, 검증이 꺼진 Reminder에는 기존 완료 흐름을 적용한다.
- **AC7.1.3:** Given 다중 담당자·복수 검증자·취소·만료·재알림·검증자 알림이 관련될 때, Then 미결정 Q-063 세부사항을 임의로 가정하지 않는다.

### US7.2 — 완료 검증 요청 승인 또는 거절하기

**스토리:** 담당자 또는 지정 검증자로서, 완료 요청을 대기 상태로 제출하고 검증자가 승인하거나 거절할 수 있기를 원한다. 검증 결과를 확정된 완료와 구분하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US7.1
- **INVEST:** 독립적인 상태 전이; 통지 방식은 Q-063에 열려 있음; 신뢰성 가치; 전이 테스트 가능; 제출·응답에 한정; 대기·승인·거절을 테스트할 수 있음.
- **AC7.2.1:** Given 검증이 켜진 Reminder의 담당자가 완료를 표시할 때, Then 회차는 즉시 완료가 아니라 검증 대기로 전환된다.
- **AC7.2.2:** Given 지정 검증자가 대기 회차를 승인할 때, Then 회차는 완료로 확정된다; 거절할 때는 미완료 상태로 돌아간다.
- **AC7.2.3:** Given 검증자 응답이 아직 없을 때, Then 회차는 검증 대기 상태로 남는다.
- **AC7.2.4:** Given 검증 요청 취소·만료·재알림·다중 담당자 상호작용이 필요할 때, Then Q-063의 후속 결정 전에는 별도 동작을 추정하지 않는다.

## 에픽 8 — 서비스 운영·복구 여정

- **AC8.1.2:** Given Q-064가 미해결일 때, Then 운영자 자격, 보고 내용·기준 시간대, 장애 신호·중복 억제, 수신자·채널·재시도 및 실제 활성화 흐름은 확정 요구처럼 만들지 않는다.

### US8.4 — 백업에서 복구하고 결과 검증하기

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US8.3
- **INVEST:** 독립적인 복구 결과; 명령·검증 방법은 협상 가능; 재해 복구 가치; rehearsal 설계 후 추정; 한 백업에서 복구; 실제 복구 가능성을 테스트할 수 있음.
- **AC8.4.1:** Given 유효한 백업과 복구 key가 별도로 있을 때, Then 운영자는 해당 백업에서 SQLite 데이터를 복구할 수 있다.
- **AC8.4.2:** Given 복구 절차를 완료할 때, Then 애플리케이션의 데이터 일관성과 서비스 시작을 확인하고 절차를 검증한다.
- **AC8.4.3:** Given 백업 시점 뒤 삭제 tombstone이 존재할 때, Then 복구 후 데이터 제공 전에 승인된 삭제 정책을 다시 적용한다.

### US8.5 — 안전하게 서비스 시작·업데이트·마이그레이션하기

**스토리:** 서비스 운영자로서, API와 Worker가 부팅 시 자동 시작되고 업데이트·DB migration 실패가 데이터 손실로 이어지지 않게 하고 싶다. 소규모 단일 노드 환경을 안정적으로 운영하기 위해서다.

- **MoSCoW:** Must Have (계획 입력)
- **선행:** US8.2, US8.3
- **INVEST:** 독립적인 운영 lifecycle 결과; 배포 도구는 협상 가능; 가용성과 복구 가치; 버전·환경 확인 후 추정; 단일 노드 시작·업데이트·migration; 중단·실패 복구를 테스트 가능.
- **AC8.5.1:** Given Raspberry Pi가 부팅될 때, Then NestJS API·Worker가 systemd로 자동 시작하고 비정상 종료 뒤 재시작한다.
- **AC8.5.2:** Given 서비스 업데이트나 DB migration이 적용될 때, Then 절차를 검증하고 실패 시 데이터와 이전 운영 상태를 보호한다.
- **AC8.5.3:** Given MVP의 자원·확장 경계를 정할 때, Then 수평 확장보다 한 노드의 단순성과 복구성을 우선한다; 구체 성능 budget은 DS-014에서 고정한다.
- **AC8.5.4:** Given 계획된 native dependency와 기술 스택을 RPi에 적용하기 전일 때, Then ARM64 호환성을 구현·빌드 검증 단계에서 확인한다.

## INVEST 종합

스토리는 한 사용자 결과 중심으로 나눴고 수용 기준은 독립적으로 확인할 수 있게 작성했다. UI 배치, 기술 선택, 세부 설계는 협상 가능하게 두었다. Story point 추정은 Domain/Functional Design에서 열린 정책과 시스템 경계가 구체화된 뒤 진행한다. 특히 US7.1–US7.2와 US8.1은 정책 미결정이 명시된 상태라 그 경계를 구현 전 닫아야 한다.
