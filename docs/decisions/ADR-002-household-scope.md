# ADR-002: MVP 가구 범위와 다중 가구 확장

- 상태: 승인
- 작성일: 2026-11-04
- 승인일: 2026-11-04
- 관련 결정: `D-020`~`D-022`
- 관련 요구사항: `F-HH-001`~`F-HH-004`, `PR-AC-027`

## 배경

MVP는 Raspberry Pi에서 실제 한 가구가 사용할 서비스다. 상용 서비스로 확장할 때 한 계정이
여러 가구에 참여할 가능성은 열어두고 싶지만, 지금부터 가구 생성·전환 화면과 여러 가구의
온보딩을 구현하면 초기 사용 흐름과 운영 범위가 커진다. Reminder와 설정은 가구 단위로
격리되어야 하고, 가구 역할과 권한도 Membership 관계를 기준으로 확인해야 한다.

## 결정

1. MVP 운영 범위는 하나의 가구 공간이다. 초기 설정으로 가구 하나를 만들고 구성원을 추가한다.
2. MVP에는 추가 가구 생성, 가입 및 가구 전환 UI를 제공하지 않는다.
3. `User`, `Household`, `Membership`를 별도 entity로 유지한다. 데이터 모델은 사용자 한 명이
   여러 Household에 가입하는 것을 막는 전역 제약을 두지 않는다.
4. Reminder, 설정, 감사 이벤트 등 가구 소유 데이터에는 `household_id`를 유지하고 관련 entity
   간 household가 일치하는지 검증한다.
5. 서비스 출시 단계에서 가구 생성·초대·전환을 제공할 때 가구별 설정·기기 동기화·권한을
   household context 기준으로 조회한다.

## 고려한 대안

### MVP부터 다중 가구 생성과 전환 제공

- 장점: 상용화에 필요한 다중 가구 흐름을 일찍 검증할 수 있다.
- 보류 이유: 현재 사용 요구는 한 가구이며, 추가 화면과 가입 흐름은 MVP 검증에 필요하지 않다.

### 사용자와 가구를 1:1로 묶기

- 기각 이유: 여러 사람이 하나의 가구를 공유해야 하고, 향후 한 사용자가 여러 가구에 참여하는
  확장도 막는다.

## 결과

### 긍정적

- MVP 화면과 운영은 한 가구에 맞게 단순하게 유지한다.
- household 경계가 데이터와 권한 모델에 남아 있어 향후 다중 가구를 추가할 수 있다.
- 가구별 설정·기기 동기화·관리 권한을 독립적으로 확장할 수 있다.

### 비용과 위험

- 데이터 모델이 단일 가구만을 전제로 한 간단한 1:1 구조보다 조금 복잡하다.
- MVP에서 가구가 하나뿐이어도 API는 household context와 사용자 membership를 일관되게 검증해야 한다.
- 단일 가구 사용 흐름을 다중 가구 기능이 이미 구현된 것처럼 문서나 UI에 표현하지 않아야 한다.

## 검증 조건

- 서로 다른 개인 계정이 같은 household에 활성 Membership를 가질 수 있다.
- 모든 household 소유 데이터는 `household_id`로 범위가 지정된다.
- schema/API model에는 사용자당 household 하나만 허용하는 전역 unique 제약이 없다.
- MVP navigation에는 다중 가구 생성·선택·전환 기능이 없다.
- 향후 다중 가구를 지원해도 household ID가 다른 사용자는 각 household 데이터를 교차 조회할 수 없다.
