# Notify Me 구현 작업 단위

## Sources

승인된 도메인 설계의 `components.md`, `decisions.md`와 `requirements.md`, `stories.md`를 기준으로 작성했다.

## Unit Definitions

| Unit ID | Directory | Kind | Deployment | Complexity | 범위 |
| --- | --- | --- | --- | --- | --- |
| U1 | u1-core-flow | service | 공유 서버·공유 웹 | M | 실제 웹·API·SQLite에서 초기 가구, 인증, 리마인더 등록·조회 |
| U2 | u2-household-and-settings | service | 공유 서버에 포함 | M | 초대·역할·접근 회수, 가구·계정 값과 설정 카탈로그 |
| U3 | u3-reminder-workflows | service | 공유 서버에 포함 | L | 담당자·조건·반복·회차·완료 검증·목록·이력·보관·삭제 |
| U4 | u4-android-notifications | service | Android 앱과 공유 서버의 동기화 모듈 | L | 설치 등록과 권한, 동기화와 시간·장소 알림 |
| U5 | u5-operations-and-recovery | service | 운영 작업 및 Raspberry Pi 실행 구성 | L | 상태·보고·장애 알림, 백업·복구, 실행·업데이트 |

복잡도는 상대 추정치다. 서버 단위는 기존 모듈형 모놀리스와 공유 SQLite 안에서 실행하며, 각 기능 단위에서 같은 웹 UI에 필요한 화면을 추가한다.

## Unit Responsibilities

- **U1 최소 통합 흐름.** Firebase Authentication의 Google 로그인 어댑터, 내부 사용자 매핑, 세션 만료·취소 거부, 로그아웃을 구현한다. 검증된 계정으로 초기 가구와 최초 Admin을 한 트랜잭션에서 만들며 초기화 명령 재실행은 중복 생성 없이 실패한다. 인가된 사용자가 웹에서 승인된 기본값으로 리마인더를 등록하고 실제 SQLite에 저장된 데이터를 서버 재시작 후 조회할 수 있게 한다.
- **U2 가구와 설정.** 일회용 초대, 구성원 역할, 마지막 Admin 보호와 접근 회수 상태를 정의한다. 설정 카탈로그와 가구·사용자 값을 관리하고 한국어·영어 및 표시 시간대 기반을 제공한다. 설치와 Reminder 값은 각 경계에서 관리한다.
- **U3 리마인더 업무.** 업무 수명주기, 반복·회차·완료 검증과 사용자 이력을 담당한다. 여러 모듈의 쓰기가 필요한 서버 명령을 조정한다. 구성원 접근 회수와 배정 종료, 반경 정책과 기존 Trigger 변경은 같은 서버 트랜잭션에서 처리한다. 설치 계획을 묶을 수 있는 진입점을 제공한다. 영구 삭제 성공은 운영 DB 변경과 독립된 복구용 삭제 표지의 확정 기록을 모두 확인한 뒤 응답한다.
- **U4 Android 알림과 동기화.** 서버 대상 상태를 설치에 반영한다. FCM은 변경 신호를 보내고 OS가 실제 알림을 실행한다. 위치 용량 검사와 설치 예약 계획을 U3 명령에 연결한다. 가구 회수 신호 또는 후속 가구 접근 거부를 받으면 기기의 해당 캐시·로컬 예약·지오펜스를 정리한다.
- **U5 운영과 복구.** 운영 진단, 선택적 보고·장애 알림, 서비스 실행 구성과 백업·복구 작업을 제공한다. 백업의 기준 위치부터 복구 직전까지 필요한 삭제 표지의 완전성·무결성을 확인하고, 재적용과 검증을 마친 뒤 데이터 제공을 허용한다. 필요한 기록이 없거나 상태·적용 결과를 검증할 수 없으면 서비스를 닫은 상태로 유지한다.

## U1 인증 검증 범위

| 검증 | 환경과 합격 기준 |
| --- | --- |
| 로컬 통합 검증 | 테스트용 인증 공급자나 로컬 에뮬레이터에 합성 사용자와 테스트 자격 증명을 사용한다. 앱의 인증 미들웨어와 가구 권한 검사를 통과하는 웹·API·SQLite 흐름에서 유효·만료·취소된 인증, 로그아웃 후 접근 거부, 최초 Admin 생성 성공·실패의 원자성, 부트스트랩 재실행 보호를 확인한다. |
| 실제 공급자 연동 검증 | 별도로 승인된 비운영 Firebase 프로젝트와 Google 테스트 계정으로 로그인, 검증된 신원의 내부 사용자 매핑, 세션 만료·로그아웃 후 접근 거부 및 실제 검증된 Admin 신원으로 초기화하는 흐름을 확인한다. 승인된 환경이나 자격 증명이 마련되기 전에는 검증 대기로 기록한다. 로컬 통합 검증 결과는 별도로 기록한다. |

검증 명령과 실행 시점은 Delivery Planning에서 구체화한다. 운영 자격 증명은 테스트에 사용하지 않는다.

## Boundary Rationale

기능을 관통하는 단위는 사용자 흐름을 실행해 확인할 수 있다. UI·API·데이터별 분할은 소유 역할을 단순하게 하지만 검증할 때 세 작업이 모두 필요하다. 서버를 독립 배포로 나누면 장애를 분리할 수 있지만 가구·업무·예약 변경을 함께 저장하기 어렵고 Raspberry Pi 운영 부담이 커진다. 각 기능의 소유권을 공유 서버 안에서 유지한다. 열린 질문은 결정 등록부에서 추적한다.
