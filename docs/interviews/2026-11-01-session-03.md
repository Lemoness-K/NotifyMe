# 사용자 인터뷰 03 — 네트워크·담당자·장소 알림

- 날짜: 2026-11-01
- 결정: `D-011`
- 관련 기준 문서: [사용자 결정 및 질문 등록부](../decision-register.md)

> Q ID의 현재 상태와 확정 내용은 사용자 결정 및 질문 등록부를 기준으로 하며, 이 문서는 당시 대화와 답변을 보존한다.

사용자는 테스트 단계부터 집 안팎에서 서버에 상시 접속할 수 있다고 가정하도록 요청했다.
이에 따라 MVP는 인터넷 HTTPS를 통해 조회·생성·수정·삭제·완료를 서버에 반영한다.
기존 LAN 전용 및 귀가 후 동기화 결정 `D-001`, `D-002`, `D-009`는 폐기한다.
오프라인 편집은 이 전제에서 MVP 범위 밖이다. 실제 서버 공개나 라우터 변경은 수행하지 않았다.

네트워크 연결과 별개로 Android 앱이 닫힌 상태에서 새로운 변경을 기기에 전달할 방법과
허용 지연은 후속 인터뷰에서 정한다. FCM은 가능한 후보이나 아직 확정하지 않았다.

## 담당자

사용자는 리마인더 하나에 담당자를 여러 명 지정할 수 있어야 한다고 답했다(`D-012`).
한 사람이라도 완료하면 업무 자체가 완료된다. 같은 일을 각자 따로 완료해야 한다면
사람별로 별도 업무를 할당한다(`D-013`, `Q-010` 해결). 기존 `D-010`에 따라 완료 권한은
담당자뿐 아니라 같은 가구의 모든 참여자에게 있다.

## 장소 조건

장소 알림은 진입, 이탈, 몇 분 이상 머무름, 이탈 후 몇 분 경과를 각각 알림 기준으로
선택할 수 있어야 한다. 사용자는 GPS 오차가 불가피함을 받아들인다(`D-014`). 이후 사용자는
"조합"이라는 표현이 부정확했다고 정정했다. 이는 AND/OR 규칙 엔진 요구가 아니다.
최소·최대 초기값, 슬라이더 간격, 재알림 정책과 허용 지연은 `Q-013`에서 확인한다.

## 후속 결정 — 알림 기준 하나 선택

- 날짜: 2026-11-04
- 결정: `D-015`

사용자는 한 Reminder에 시간 기준과 장소 기준을 함께 설정할 수 없으며, 둘 중 하나만
선택하도록 결정했다. 장소 기준을 선택한 경우에도 진입·이탈·머무름·이탈 후 경과 중
알릴 이벤트 하나를 고른다. 시간과 장소를 결합하는 AND/OR 규칙은 요구하지 않는다.
이에 따라 기존 질문 `Q-006` 및 `Q-023`은 해결했다.

## 후속 결정 — 이탈 후 타이머와 재진입

- 날짜: 2026-11-04
- 결정: `D-016`

사용자는 `AFTER_EXIT(N)` 타이머가 끝나기 전에 장소에 다시 들어오면 타이머를 리셋하고,
다음에 다시 나간 시점부터 N분을 새로 세는 동작을 선택했다. `Q-013`의 재진입 정책은
이 결정으로 해결했으며, 최소·최대 초기값·슬라이더 간격과 재알림·허용 지연은 계속 확인한다.

## 후속 결정 — 장소별 반경 조정

- 날짜: 2026-11-04
- 결정: `D-017`

사용자는 장소 반경에 기본값을 두고, 리마인더를 추가하거나 수정할 때 슬라이더로
반경을 조절할 수 있기를 원한다. 반경은 미터 단위로 Reminder별 저장한다. 50m와 100m는
기본값 후보로 언급했다. 이후 기본 반경은 100m로 정하고, 옵션 메뉴에서 최소·최대·기본값을
설정할 수 있도록 결정했다(`D-018`). 최소·최대 초기값과 슬라이더 간격은 `Q-013`에 남긴다.

## 후속 결정 — 장소 반경 옵션

- 날짜: 2026-11-04
- 결정: `D-018`

사용자는 옵션 메뉴에서 장소 반경의 최소값·최대값·기본값을 설정하고 싶다고 했다. 초기
기본값은 100m로 한다. 장소 Trigger별 반경은 계속 슬라이더로 조정한다(`D-017`). 사용자는
이 옵션이 가구 공통 설정이어야 한다고 명확히 했다(`D-018`). Admin만 편집하도록 결정했다(`D-020`, `Q-024` 해결).

## 후속 결정 — 앱 설정과 선택 기능 관리

- 날짜: 2026-11-04
- 결정: `D-019`

사용자는 장소 반경뿐 아니라 서비스 전반을 위한 별도 Settings 화면을 요청했다. 화면은
가구 설정과 개인 설정을 나누고, OS 권한·현재 기기 capability는 별도 상태로 구분한다.
선택적으로 끄거나 값을 조정할 수 있는 모든 기능은 설정 카탈로그에 등록한다. 기능을
추가·변경·제거할 때마다 범위, 기본값, 제한, 비활성화 동작, 기존 데이터 처리와 마이그레이션을
함께 설계하도록 프로젝트 지침에도 반영한다.

## 후속 결정 — 가구 역할과 설정 권한

- 날짜: 2026-11-04
- 결정: `D-020`

사용자는 가구 역할을 Admin과 Member로 나누고, household settings는 Admin만 변경하도록
제안했다. 두 역할 모두 reminder CRUD와 완료 권한을 유지한다(`D-010`). 기존 Owner의 구성원
초대·제거 권한은 Admin에게 이어지는 설계로 반영했다. 사용자는 두 역할이 각각 0명 이상일 수
있기를 제안했으나, 활성 가구에 Admin이 0명일 경우 설정·역할 관리가 불가능해질 수 있어 최소
한 명을 유지할 것을 권고했다. 사용자가 이에 동의하고 마지막 Admin 인계 방식을 확정해
`D-021`에 기록했으며, 당시 질문 `Q-025`는 해결했다.

## 후속 결정 — 마지막 Admin 보호

- 날짜: 2026-11-04
- 결정: `D-021`

사용자는 활성 가구에 Admin이 최소 한 명 있어야 한다고 동의했다. 마지막 Admin이 나가거나
Member로 강등되기 전에 다른 구성원에게 Admin 역할을 넘긴다. 인계 대상이 없으면 해당 변경을
거부한다. 관리자 최소 수와 인계 방식 질문 `Q-025`는 해결했다.

## 후속 결정 — MVP 단일 가구와 다중 가구 확장 경계

- 날짜: 2026-11-04
- 결정: `D-022`

사용자는 향후 여러 가구에 참여할 수 있도록 데이터 구조를 열어두되, 지금 실제 필요한 범위는
하나의 가구라고 확인했다. MVP는 가구 하나만 운영하고 추가 가구 생성·전환 화면은 제공하지
않는다. User, Household, Membership를 분리하고 모든 가구 소유 데이터를 `household_id`로
격리해 서비스 출시를 검토할 때 다중 가구 기능을 추가할 수 있게 한다. 원래 인터뷰 질문
`Q-003` 중 가구 수 범위는 이 결정으로 정리했다. 개인 로그인과 구성원 권한은 기존 계정 모델과
`D-010`, `D-020`에 반영했다. 계정·가구 종료 정책은 `Q-009`에 남아 있으며, Reminder 삭제·이력
보존은 `D-031`, `D-032`, `D-058`에서 정하고 데이터 내보내기는 `D-067`에서 후속 기능으로 계획했다.
구성원 초대 방식은 `D-023`에서 초대 URL로 정리했다.

## 후속 결정 — 링크 초대 가입

- 날짜: 2026-11-04
- 결정: `D-023`

사용자는 URL 안에 코드를 넣어 링크를 누르면 가입할 수 있는 흐름을 제안했다. 이 방식을 채택한다.
Admin은 일회용 코드를 담은 URL을 만들어 직접 공유한다. 초대 대상자는 링크에서 계정을 만들거나
로그인해 코드를 다시 입력하지 않고 가입을 완료한다. MVP에는 이메일 발송 기능을 넣지 않는다.
안전하게 처리하기 위해 URL 조회만으로 초대를 소비하지 않고, 인증된 수락 요청에서 한 번만
Membership를 만든다. 토큰 원문 대신 hash를 저장하며 만료·취소를 지원한다. 만료 기간은
`D-028`에서 24시간으로 정하고, 대상 Google 계정에 binding하기로 `D-029`에서 결정했다.
초대 방식 질문 `Q-026`과 초대 정책 `Q-028`은 해결했다.

## 후속 결정 — 계정 인증 방식

- 날짜: 2026-11-04
- 결정: `D-024`

사용자는 ID/비밀번호를 직접 관리할지, Google 로그인이나 외부 인증 서비스를 사용할지와 비용을
확인하고 싶다고 했다. 비용·운영을 비교한 추천안을 채택해 MVP는 Firebase Authentication의
Google provider로 로그인한다. 별도 내부 ID/비밀번호 로그인은 제공하지 않는다. RPi는 Firebase
identity를 내부 User ID에 매핑하고, 내부 ID는 reminder와 Membership 관계·인가에만 사용한다.
사용자는 내부 ID를 입력하거나 관리하지 않는다. 현재 공개 요금과 선택 이유는
[보안·개인정보 설계](../07-security-and-privacy.md#21-인증-방식과-비용-선택지)에 기록했다.
기존 질문 `Q-029`는 해결했고, 상용화 시 추가 로그인 제공자 범위는 `Q-030`에서 다룬다.

## Q-031 — 저장 데이터 보안과 자동 재시작

- 날짜: 2026-11-04, 후속 결정: 2026-11-06
- 상태: 위협 범위와 재시작 정책 결정 (`D-025`)

사용자는 내부 데이터 저장 시 추가 보안 검토가 필요한지 물었다. 가구 업무 데이터, 장소 좌표,
Firebase identity, push/invite token, 운영 로그와 백업을 민감도별로 분류하고 DB·백업 저장
암호화, key 분리·복구, 최소 권한, 로그 제외 원칙을 [보안·개인정보 설계](../07-security-and-privacy.md)에
추가했다. 이후 사용자는 집에서 운영하므로 기기 통째 분실과 물리적 저장장치 열람 위험은 제외하고,
웹을 통한 보안에 집중하겠다고 했다. RPi가 정전·재부팅 뒤 수동 key 입력 없이 자동 시작하도록
결정했다. 전체 디스크 암호화는 MVP의 필수 요건에서 제외하며, 운영 DB 암호화는 웹/API 침입을
막는 통제로 간주하지 않고 DB 선택 뒤 구체적 필요를 검토한다. 별도 보관 백업은 암호화한다.

보안 설계에서 다룰 원격 위협은 Firebase token 검증, 매 요청의 서버측 household·객체 권한 검사,
TLS, 입력 검증과 안전한 DB 질의, 초대 비밀값 보호, endpoint 속도 제한, 비밀값 관리, 최소 권한,
로그의 민감정보 제외, OS·dependency 업데이트다. 장소 좌표와 알림 내용은 가족 생활 정보로
다룬다. FCM payload의 세부 정책은 `Q-018`에 남긴다.

## 후속 결정 — Android 잠금 화면 알림

- 날짜: 2026-11-06
- 결정: `D-026`

사용자는 잠금 화면 알림 내용 공개가 Android 설정의 일부인지 확인했다. Android OS에서 사용자가
알림 공개 여부를 조절하며, 앱도 알림별 공개 수준과 민감 정보가 가려졌을 때 표시할 `publicVersion`을
지정한다. 이에 따라 MVP는 별도 앱 설정을 만들지 않고, 민감 알림을 `VISIBILITY_PRIVATE`로 보내며
가려진 화면에는 일반 문구(예: “새 리마인더가 있어요”)를 표시한다. 필요하면 앱에서 Android 알림
설정 화면으로 이동시킨다. `Q-015`는 이 결정으로 해결했다.

## 후속 결정 — 초대 가입자의 역할

- 날짜: 2026-11-06
- 결정: `D-027`

사용자는 초대 링크 가입자는 Member로 추가하고, 기존 Admin이 가입 후 필요하면 Admin으로
승격하는 방식을 선택했다. 초대 링크 자체는 관리자 권한을 부여하지 않는다. Member도 모든
리마인더를 생성·수정·삭제·완료할 수 있으므로 바로 가구 기능을 사용할 수 있다. `Q-027`은 해결했다.

## 후속 결정 — 초대 링크 유효 기간

- 날짜: 2026-11-06
- 결정: `D-028`

사용자는 초대 링크를 발급 후 24시간 동안 유효하게 하기로 했다. 초대 레코드의 저장량은 링크가
하루 또는 수 주 유효한지에 따라 의미 있게 달라지지 않는다. 이 기간은 서버 자원 절약보다 링크가
노출될 수 있는 시간을 줄이는 효과가 있다. 특정 Google 계정 binding 여부는 `Q-028`에 이어서 결정했다(`D-029`).

## 후속 결정 — 초대 대상을 Google 계정에 binding

- 날짜: 2026-11-06
- 결정: `D-029`

사용자는 초대 링크를 지정된 Google 계정에 묶는 방식을 선택했다. Admin은 발급 때 초대 대상의
Google 이메일을 입력한다. 수락 시 서버는 Firebase ID token과 Google provider, `email_verified=true`,
인증 이메일과 초대 이메일의 일치를 검증한다. 일치하지 않으면 가입을 거부하고 token을 소비하지 않는다.
내부 사용자 관계는 이메일이 아니라 Firebase identity와 내부 `User.id`를 기준으로 유지한다.
`Q-028`은 해결했다.

## 후속 결정 — 반복·단발 미완료 알림 처리

- 날짜: 2026-11-06
- 결정: `D-030`

사용자는 반복 Reminder에서 새 회차가 예정 시각에 도달하면 이전 미완료 회차를 `MISSED`로 닫고
이력에 남기는 방식을 선택했다. 새 회차는 원래 일정을 유지한다. 단발 Reminder는 시간 경과나
장소 알림 발생만으로 닫지 않고 사용자가 완료하거나 취소할 때까지 활성 할 일에 남긴다. 시간
기준 단발 항목은 기한 초과 목록에서 확인한다. 반복 회차 미완료 정책 질문 `Q-007`을 해결했다.

## 후속 결정 — 완료·놓침 이력 보존

- 날짜: 2026-11-06
- 결정: `D-031`

사용자는 완료·놓침 회차 이력을 기간 제한 없이 보존하는 추천안을 선택했다. 연령에 따른 자동
삭제는 하지 않으며, 저장 공간이 부족해지면 그 시점에 대안을 검토한다. 당시 리마인더 삭제와 변경·감사
기록, 계정·가구 종료 및 데이터 내보내기는 `Q-009`로 남겼다. 이후 Reminder 삭제·백업 정책은
`D-032`, `D-058`, 내보내기 구현 연기는 `D-067`에서 정했으며 계정·가구 종료만 `Q-009`에 남아 있다.

## 후속 결정 — Reminder 보관과 영구 삭제

- 날짜: 2026-11-06
- 결정: `D-032`

사용자는 Reminder 삭제를 복원 가능한 보관과 분리했다. 보관하면 보관함으로 이동해 나중에 복원할
수 있다. 보관함에서도 영구 삭제할 수 있고, 활성 목록에서도 영구 삭제가 가능해야 한다. 영구
삭제한 Reminder와 이력은 사용자 관점에서 되돌릴 수 없도록 한다. 당시 서버 동기화 tombstone과
백업의 물리 제거 시점은 `Q-009`에 남겼고 이후 `D-058`에서 해결했다.

사용자는 Jira처럼 Reminder의 상태와 상태 전이를 다이어그램으로 볼 수 있다는 아이디어를 냈다.
당시 고정 상태 흐름을 보여줄지 사용자 정의 흐름까지 제공할지는 `Q-033`으로 남겼다. 이후 `D-035`에서
고정 상태 흐름과 이력 화면을 선택하고 사용자 정의 상태는 MVP에서 제외했다. 보관 중 반복·알림 정지와
복원 시 지난 반복 회차 처리는 당시 미결정이었으며 `D-033`에서 정리했다. 보관 시작 전에 이미 생성된
미완료 회차의 복원 후 처리는 `D-034`에서 결정했다.

## 후속 결정 — 반복 Reminder 보관과 재개

- 날짜: 2026-11-06
- 결정: `D-033`

사용자는 반복 Reminder도 보관할 수 있게 하고, 추천한 대로 보관 기간에 예정됐던 회차는 새로
만들거나 `MISSED`로 기록하지 않으며 복원 후 다음 미래 회차부터 원래 반복 규칙을 이어가기로 했다.
보관 중 알림과 새 반복 회차 생성은 멈춘다. 보관 시작 전에 이미 생성된 미완료 회차의 복원 후
처리는 추가 확인을 위해 `Q-034`에 남겼다.

## 후속 결정 — 보관 전 생성된 미완료 회차 복원

- 날짜: 2026-11-06
- 결정: `D-034`

사용자는 보관 전에 이미 생성된 미완료 회차는 그대로 보관하고, 복원하면 다시 할 일로 표시하는
방식을 정했다. 시간 Trigger의 예정 시각이 지났으면 `OVERDUE`로 보이고 과거 알림은 재생하지 않는다.
장소 Trigger는 복원 시 다시 등록한다. 이에 따라 `Q-034`를 해결했다.

## 후속 결정 — Reminder 현재 상태와 이력 화면

- 날짜: 2026-11-07
- 결정: `D-035`

사용자는 Reminder 목록·상세에서 현재 상태를 뱃지로 보고, 상세의 이력 버튼을 누르면 해당
Reminder의 상태 흐름 다이어그램과 변경 이력 목록을 함께 보는 구성을 선택했다. Reminder 자체의
보관·삭제 수명주기와 각 수행 회차의 예정·완료·놓침 진행 상태는 별도 흐름으로 표시하고, 각 흐름에서
현재 상태를 강조한다. MVP에서 상태나 전이를 사용자 정의하지 않는다. 목록에서 우선 표시할 상태 뱃지는
`D-036`에서 정했다. 이력에 포함할 변경과 변경 전·후 값의 범위는 `D-037`에서 결정했다.

## 후속 결정 — 목록 상태 뱃지 기준

사용자는 Reminder 수명주기와 개별 할 일 회차의 진행 상태를 별도 축으로 관리하는 데 동의했다.
목록의 주 상태 뱃지는 개별 Occurrence 진행 상태를 보여준다. `ACTIVE`는 Reminder 정의의 수명주기이고,
`PENDING`/예정·완료·놓침은 수행 회차의 진행 상태다. 보관된 Reminder는 보관함에서 수명주기를
확인한다. 따라서 `Q-036`을 해결했다.

## 후속 결정 — 변경 이력 항목과 값 범위

- 날짜: 2026-11-07
- 결정: `D-037`

사용자는 추천한 변경 이력 범위를 선택했다. Reminder 생성과 주요 필드·담당자·Trigger·반복 설정 변경,

바뀐 항목 및 이전·새 값을 표시한다. 자동으로 `MISSED` 처리된 회차는 변경자를 시스템으로 표시한다.
장소 변경에는 장소명과 반경만 표시하고 정확한 GPS 좌표는 포함하지 않는다. 영구 삭제 후에는 이력을
사용자 화면에서 조회할 수 없다. 이에 따라 `Q-035`를 해결했다.

## 후속 결정 — 장소 반경 초기 범위

기존 Reminder 반경 처리, 재알림 정책과 허용 지연은 `Q-013`에 남긴다.

## 후속 결정 — 장소 반경 슬라이더 간격

- 날짜: 2026-11-07

사용자는 추천한 대로 장소 반경 슬라이더를 25m 단위로 조정하기로 했다. 실제로 사용한 뒤 불편하면
간격을 재조정할 수 있도록 초기 UI 결정으로 둔다. 설정 범위 변경 후 기존 반경 처리, 재알림 정책과
허용 지연은 `Q-013`에 남긴다.

## 후속 결정 — 장소 반경 범위 변경 시 기존 항목 조정

- 날짜: 2026-11-08
- 결정: `D-040`

사용자는 Admin이 가구의 장소 반경 최소값·최대값을 바꿀 때 범위 밖인 기존 Reminder 반경을 새
경계값으로 자동 조정하는 방식을 선택했다. 가구 설정과 활성·보관 LOCATION Trigger 값은 한 번에
저장한다. 각 반경 변경은 설정을 바꾼 Admin, 이전 값, 새 값과 함께 이력에 기록한다. 커밋 뒤 활성
기기 지오펜스를 새 반경으로 갱신하고, 보관된 Reminder는 복원 시 새 반경을 등록한다. 이에 따라
`Q-013`의 기존 반경 처리 항목을 해결했다.

## 후속 결정 — 새 장소 조건 event마다 재알림

- 날짜: 2026-11-08
- 결정: `D-041`

사용자는 추천한 재알림 방식을 선택했다. 회차가 미완료인 동안 새로 인식된 장소 조건 event마다 한 번
알림한다. 동일 event callback의 중복 알림은 막고, 같은 진입 또는 연속 머무름 상태가 이어지는 동안
반복하지 않는다. 이후의 새 진입·이탈 전이, 새 연속 머무름 구간, 재진입으로 타이머가 초기화된 뒤
새로 만료된 `AFTER_EXIT` countdown은 각각 새로운 조건 event로 본다. 회차가 완료·취소·놓침 상태가
되거나 Reminder가 보관되면 추가 알림하지 않는다. 알림은 회차를 자동 완료하지 않는다. 이 결정으로
`Q-013` 중 재알림 정책을 해결했으며, 장소 event 허용 지연과 위치 데이터 보존 기간은 남아 있다
([ADR-009](../decisions/ADR-009-location-alert-retriggering.md)).

## 후속 결정 — 장소 조건 감지 직후 알림

- 날짜: 2026-11-08
- 결정: `D-042`

사용자는 기기가 장소 조건을 감지하는 즉시 알림을 표시하기로 했다. 앱은 서버 동기화, FCM 등 원격
전달 응답이나 재시도를 기다리지 않고 로컬 시스템 알림을 게시하며, event 기록 동기화는 별도로
진행한다. “즉시”는 Android가 event를 앱에 전달한 뒤의 처리 기준이다. Android geofence callback
자체의 도착 시각은 OS 및 위치 조건에 따라 지연되거나 누락될 수 있으므로 고정 감지 SLA를 약속하지
않는다. 이로써 `Q-013`의 알림 지연 부분을 정리하고, 위치 설정·장소 event 데이터 보존 기간만 남긴다
([ADR-010](../decisions/ADR-010-location-alert-immediacy.md)).

## 후속 결정 — 위치 데이터 최소화와 보존 기간

- 날짜: 2026-11-08
- 결정: `D-043`

사용자는 사용자의 실시간 GPS 좌표나 이동 경로를 서버로 전송하거나 보관할 필요가 없다고 확인했다.
앱 데이터에도 현재 위치 sample이나 경로를 저장하지 않는다. 사용자가 장소 Reminder에 지정한
geofence 중심 좌표와 반경은 기능 동작에 필요한 Trigger 설정으로 서버와 대상 기기에 유지한다.
서버에는 event ID·설치 ID·Occurrence·trigger revision·조건 종류·감지 시각·처리 결과만 남기며,
감지 시점부터 30일 후 삭제한다. 기기의 local event journal에는 중복 방지·동기화에 필요한 비좌표
metadata만 두고 서버 확인 뒤 삭제한다. 이에 따라 `Q-013`을 해결했다
([ADR-011](../decisions/ADR-011-location-data-minimization-and-retention.md)).

## 후속 결정 — 백그라운드 위치 권한 거부 시 동작

- 날짜: 2026-11-08
- 결정: `D-044`

사용자는 추천한 권한 거부 처리에 동의했다. 백그라운드 위치 권한이 없어도 LOCATION Reminder를
저장하고, 권한이 없는 설치에만 장소 알림 불가 상태와 Android 설정 바로가기를 표시한다. 권한 회복
뒤 해당 설치의 지오펜스를 다시 등록한다. 권한 상태는 설치별로 관리하므로 다른 구성원 기기는 계속
독립적으로 동작한다. 앱은 Android OS 설정을 강제로 바꾸지 않는다([ADR-012](../decisions/ADR-012-location-permission-degraded-mode.md)).

## 후속 결정 — 알림 수신 대상

- 날짜: 2026-11-08
- 결정: `D-045`

사용자는 Reminder 알림을 지정 담당자에게만 보내기로 했다. 각 담당자의 알림 가능한 등록 기기가
시간 알림 수신 대상이며, 장소 geofence도 담당자의 권한이 허용된 기기에만 설치한다. 비담당 가구
구성원은 기존 권한대로 Reminder를 조회·수정·완료할 수 있지만 알림은 받지 않는다. 한 구성원이
Occurrence를 완료하면 다른 담당자 기기의 예약 알림과 geofence를 취소한다([ADR-013](../decisions/ADR-013-assignee-only-notifications.md)).

## 후속 결정 — 시간 알림 예약과 FCM 동기화 신호

- 날짜: 2026-11-08
- 결정: `D-046`

사용자는 추천한 전달 원칙을 선택했다. 시간 알림은 담당자 기기에서 Android local alarm으로 예약하고,
FCM은 영향을 받는 담당자 설치에 Reminder 변경을 알리는 비사용자용 sync signal로만 사용한다. 수신
기기는 서버 revision을 fetch해 시간 예약과 geofence를 reconcile한다. FCM signal은 notification tray에
표시하지 않으며, 앱 시작·foreground 복귀·부팅 시에도 서버 상태를 다시 맞춘다. FCM 전달은 best-effort로
두고 고정 지연을 약속하지 않는다. 이미 기기에 설치된 시간 알림은 FCM 수신 여부와 무관하게 울린다
([ADR-014](../decisions/ADR-014-local-alarms-and-fcm-sync-signals.md)).

## 후속 결정 — 정확 알람 권한 거부 시 동작

- 날짜: 2026-11-08
- 결정: `D-047`

사용자는 정확 알람 권한을 요청하는 추천안을 선택했다. 사용자가 거부해도 Reminder 저장을 허용하고,
해당 설치에는 지연될 수 있는 부정확 알람을 예약한다. 설치별 상태에 알림 지연 가능 안내와 Android
설정 바로가기를 보여준다. 권한을 허용하거나 다시 허용하면 해당 설치의 예약을 정확 알람으로 조정하고,
회수되면 부정확 알람으로 낮춘다. 이 권한 상태는 가구·개인 설정이 아니라 설치 capability다. 허용 지연,
재시도와 오래 지난 알림의 처리 한계는 `Q-020`에 남긴다
([ADR-015](../decisions/ADR-015-exact-alarm-permission-fallback.md)).

## 후속 결정 — 늦은 시간 알림의 catch-up 기간

- 날짜: 2026-11-08
- 결정: `D-048`

사용자는 추천한 24시간 cutoff를 선택했다. 활성 Reminder의 `PENDING` 회차는 담당자 각 설치에서 예정 시각부터
24시간 이내(경계 포함) 늦은 알림을 한 번 표시한다. 그 이후 도착한 callback이나 앱 시작·재부팅 뒤 발견한 과거
예약은 사용자 알림으로 표시하지 않는다. 이 억제는 할 일 자체를 닫지 않으며, 단발 회차는 기존대로
기한 초과 목록에 남긴다. 완료·취소·놓침 회차와 보관 Reminder는 항상 알림을 억제한다
([ADR-016](../decisions/ADR-016-time-alarm-catch-up-window.md)).

## 후속 결정 — FCM 변경 동기화 신호의 재시도와 만료

- 날짜: 2026-11-08
- 결정: `D-049`

사용자는 추천한 24시간 정책을 선택했다. 서버 Outbox는 변경 시각부터 24시간 뒤 만료되며, 일시적인 FCM
발송 오류는 그 기간에만 exponential backoff로 재시도한다. FCM TTL에는 남은 유효시간을 넣어 재시도할 때
메시지 수명을 다시 24시간으로 늘리지 않는다. FCM이 요청을 수락하면 서버는 재발송하지 않으며 실제 기기
수신을 보장하지 않는다. 만료·미수신 변경은 앱 시작·foreground 복귀·부팅 동기화로 복구한다
([ADR-017](../decisions/ADR-017-fcm-change-signal-retry-and-ttl.md)). 이에 따라 `Q-020`을 해결했다.

## 후속 결정 — Android 배터리 최적화 대응

- 날짜: 2026-11-08
- 결정: `D-051`

Android Doze와 제조사별 절전 정책은 앱의 백그라운드 작업이나 위치 감지 시점에 영향을 줄 수 있다. 공식 문서는 백그라운드 geofence 반응이 늦어질 수 있다고 설명하며, 대부분의 앱은 배터리 최적화 예외를 직접 요청하지 않는 편이 적절하다고 안내한다([위치·배터리 가이드](https://developer.android.com/develop/sensors-and-location/location/battery), [Doze·App Standby 가이드](https://developer.android.com/training/monitoring-device-state/doze-standby)).

사용자는 앱이 Android 배터리 최적화 예외를 직접 요청할 필요가 없다는 추천안에 동의했다. 앱은 설치별로 확인 가능한 알림·정확 알람·위치 capability를 보여주고, 필요한 경우 사용자가 OS 설정을 직접 확인할 안내·바로가기를 제공한다. 제조사별 절전 동작은 실기기 검증 대상으로 두며, 예외 설정이 모든 지연을 해결한다고 보장하지 않는다. 강제 종료 정책은 별도 결정 `D-050`을 계속 적용한다([ADR-019](../decisions/ADR-019-android-battery-optimization.md)).

## 후속 결정 — 반응형 공유 Web UI와 플랫폼별 네이티브 어댑터

- 날짜: 2026-11-08
- 결정: `D-052`

사용자는 가능한 한 Web 앱에서 기능을 처리하고, Android/iOS 등 운영체제별 기능만 네이티브 어댑터로 두는 방향을 선택했다. 공유 UI는 TypeScript 기반 반응형 Web 앱으로 모바일·태블릿·데스크톱 브라우저와 Capacitor WebView에서 재사용한다. 브라우저는 주요 업무 CRUD를 지원하지만 OS background 알림·geofence 기능은 지원되는 native installation에 한정한다. Android는 Kotlin capability별 모듈로 구현하고, 후속 iOS는 같은 platform-neutral port/event contract에 Swift 모듈을 붙인다. 당시 framework 선택은 `Q-016`에 남겼으며, Web UI는 이후 `D-054`에서 React Router + Vite SPA로, API는 `D-055`에서 NestJS로 정했다([ADR-020](../decisions/ADR-020-responsive-web-and-platform-adapters.md)).

## 후속 결정 — MVP 데이터베이스

- 날짜: 2026-11-08
- 결정: `D-053`

MVP는 한 가구와 소수의 동시 사용자를 Raspberry Pi 한 대에서 운영한다. SQLite는 별도 DB 서버를 설정·운영하지 않아도 되고 저 writer 동시성의 애플리케이션에 적합하지만, 한 DB 파일에는 한 번에 한 writer만 쓸 수 있다. PostgreSQL은 ARM Linux를 지원하는 client/server DB이며, 다중 가구와 worker 확장을 고려하기 좋다([SQLite 사용 가이드](https://www.sqlite.org/whentouse.html), [PostgreSQL 지원 플랫폼](https://www.postgresql.org/docs/current/supported-platforms.html)).

사용자는 추천안에 동의했다. MVP DB는 SQLite이며, RPi 로컬 영속 경로에 둔다. repository와 versioned migration 경계를 유지하고, 짧은 쓰기 transaction과 단일 Worker로 SQLite의 단일 writer 제약을 다룬다. 상용화 또는 동시성·다중 인스턴스 요구가 구체화될 때 PostgreSQL 전환을 재평가하며, 자동 호환된다고 가정하지 않는다([ADR-021](../decisions/ADR-021-sqlite-mvp-database.md)).

## 후속 결정 — Web UI framework

- 날짜: 2026-11-08
- 결정: `D-054`

사용자는 React Router의 framework mode를 Vite SPA mode(`ssr: false`)로 구성해 하나의 정적 Web build를 브라우저와 Capacitor WebView에서 함께 쓰는 추천안에 동의했다. UI는 서버 렌더링 없이 별도 Node.js API와 통신한다. React 공식 문서는 새 앱에서 framework 사용을 권장하고, React Router는 SPA mode와 정적 build를 지원한다([React 앱 구성](https://react.dev/learn/creating-a-react-app), [React Router SPA mode](https://reactrouter.com/how-to/spa), [Vite guide](https://vite.dev/guide/), [ADR-022](../decisions/ADR-022-react-router-vite-spa.md)).

## 후속 결정 — Node.js API framework

- 날짜: 2026-11-08
- 결정: `D-055`

사용자는 추천안에 동의해 Node.js runtime 위에서 NestJS를 API framework로 선택했다. API는 RPi에서 단일 모듈형 모놀리스로 운영하고, 인증·가구, 리마인더·회차·반복, 설정, 동기화·알림을 feature module로 구분한다. NestJS 선택은 마이크로서비스 분리를 뜻하지 않는다. 도메인 규칙은 NestJS와 DB 접근 도구에 종속되지 않도록 한다([ADR-023](../decisions/ADR-023-nestjs-api-framework.md)).

Node.js는 서버 코드를 실행하는 runtime이고 NestJS는 그 위에 API 구조와 기능별 module 관례를 제공하는 framework라는 차이를 확인했다. NestJS의 기본 HTTP adapter는 Express이며, NestJS는 Fastify와 Node.js HTTP adapter도 지원한다. 이번 설계는 NestJS framework를 선택하고, 초기 HTTP adapter는 기본값으로 시작한다([NestJS 플랫폼 문서](https://docs.nestjs.com/first-steps)).

## Q-037 — SQLite ORM/query layer 선택

- 날짜: 2026-11-08
- 결정: `D-056`

사용자는 ORM 상세를 알지 못해 추천안을 선택했다. SQLite 접근에는 Prisma ORM 7과 `@prisma/adapter-better-sqlite3`를 사용한다. Prisma schema와 SQL migration을 버전 관리하고, NestJS provider로 생성 client를 주입하되 도메인 규칙에 Prisma 타입을 노출하지 않는다. 실제 Raspberry Pi의 Node.js 버전과 ARM64 driver 호환성은 구현 단계에서 확인한다. NestJS 공식 SQLite 가이드가 Prisma 7을 기준으로 하고, 당시 npm `latest` tag가 Prisma 8 prerelease를 가리킬 수 있다고 안내하므로 호환되는 Prisma 7 major 버전을 lockfile로 고정한다([NestJS Prisma + SQLite 가이드](https://docs.nestjs.com/data/prisma), [ADR-024](../decisions/ADR-024-prisma-orm-sqlite-access.md)).

## 후속 결정 — 외부 HTTPS 진입점

- 날짜: 2026-11-08
- 결정: `D-057` (`Q-017` 해결)

사용자는 추천안에 동의해 외부 ingress로 Caddy를 선택했다. Caddy는 DDNS hostname에 대한 HTTPS 인증서를 자동 발급·갱신하고 HTTP를 HTTPS로 redirect하며, React 정적 build를 제공하고 API 요청을 NestJS로 reverse proxy한다. 라우터에서는 TCP 80/443만 Caddy로 전달하고 내부 앱·DB·관리 포트는 공개하지 않는다. 실제 DDNS hostname 선택과 port forwarding 설정은 배포 단계에서 수행하며, 이번 설계 작업에서는 네트워크 설정을 변경하지 않았다([Caddy HTTPS quick-start](https://caddyserver.com/docs/quick-starts/https), [Caddy reverse proxy quick-start](https://caddyserver.com/docs/quick-starts/reverse-proxy), [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https), [ADR-025](../decisions/ADR-025-caddy-ddns-https-ingress.md)).

## 후속 결정 — 영구 삭제와 백업 보존

- 날짜: 2026-11-08
- 결정: `D-058` (`Q-009` 중 Reminder 삭제 정책 해결)

사용자는 Reminder를 영구 삭제하면 사용자 화면과 운영 DB에서 즉시 제거하고, 사용자가 앱에서 복원할 수 없게 하기로 했다. 늦게 동기화하는 기기에 삭제를 전달할 수 있도록 Reminder ID와 delete revision만 담은 tombstone은 최대 30일 보관한다. 암호화된 재해 복구 백업도 순환 보관해 최대 30일 뒤 만료시킨다. 삭제 확인 화면에는 백업 세부사항을 표시하지 않지만, 서비스 출시 시 개인정보 처리방침에는 백업 보관·파기 방식을 공개한다. 백업 복원 전 tombstone을 재적용해 영구 삭제 항목이 일반 복구로 되살아나지 않게 한다. 실수 삭제의 복구는 사용자 기능이 아니라 운영자 전용 절차로 제한하고 감사 기록을 남긴다([ADR-026](../decisions/ADR-026-permanent-delete-and-backup-retention.md)).

개인정보 보호법은 불필요해진 개인정보의 지체 없는 파기와 복구·재생 방지 조치를 규정하고, 개인정보 처리방침에 보유 기간 및 파기 절차·방법을 포함하도록 한다. 따라서 이 백업 정책은 운영상 문서화하고 출시 전에 실제 적용 방식의 적법성을 확인한다([개인정보 보호법 제21조](https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=900078981), [제30조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1025127663)). 계정·가구 종료 시 데이터 삭제·보존은 `Q-009`에, 내보내기 구현 연기는 `D-067`에 남겼다.

## 후속 결정 — Admin의 구성원 제거와 담당 업무

- 날짜: 2026-11-09
- 결정: `D-059`

사용자는 Admin이 구성원을 제거할 때 기존 가구 업무와 기록을 보존하고 제거된 구성원의 담당을 해제하기로 했다. Membership 접근은 즉시 차단한다. 다른 담당자가 남아 있으면 업무와 알림은 계속되고, 제거된 사람이 유일한 담당자라면 현재 미완료 회차는 `PENDING`·무담당으로 남긴다. 이 회차는 다른 가구 구성원이 조회·수정·완료할 수 있으나 알림을 받지 않는다. 제거된 사용자의 기기는 접근 회수 신호를 받거나 이후 API 권한 거부를 확인할 때 해당 household 캐시·예약을 정리한다. 전달 신호는 best-effort이며 Android force-stop 제약을 따른다([ADR-027](../decisions/ADR-027-member-removal-and-unassigned-reminders.md)).

## 후속 결정 — 무담당 반복 Reminder의 일시 중지

- 날짜: 2026-11-09
- 결정: `D-060` (`Q-038` 해결)

사용자는 무담당 반복 Reminder를 종료하지 않고 일시 중지하는 추천을 선택했다. 활성 담당자가 사라지면 현재 미완료 회차를 `PENDING`·무담당으로 유지하고 규칙은 보존한다. 담당자 부재 중에는 새 회차와 알림을 만들지 않는다. 담당자를 다시 지정하면 현재 회차는 유지하고, 그 뒤 미리 생성됐으나 재지정 시각보다 과거가 된 회차는 `SKIPPED`·`NO_ACTIVE_ASSIGNEE` 사유로 기록한다. 미래에 이미 예정된 회차는 유지하고, 무담당 기간의 미생성 회차는 보충하지 않는다. 현재 회차가 다음 반복 시각까지 완료되지 않으면 기존 규칙에 따라 `MISSED`로 닫는다. 재지정 후 현재 시간 회차의 알림은 기존 24시간 지연 표시 규칙을 따른다. 일시 중지·재개와 건너뛴 회차는 `SYSTEM` actor로 이력에 남기며, 목록의 상태 뱃지는 Occurrence 진행 상태를 유지한다([ADR-028](../decisions/ADR-028-unassigned-recurrence-pause.md)).

## 후속 결정 — 월간 특정 날짜와 말일

- 날짜: 2026-11-09
- 결정: `D-061` (`Q-039` 해결)

사용자는 반복 날짜 선택이 월초·월말 두 가지만 있는 것이 아니라 정확한 날짜도 지원하기를 원했다. 월간 반복은 `특정 날짜(1~31일)` 또는 `매월 말일` 중 하나를 고른다. 정확한 날짜가 해당 월에 없으면 그달 회차를 건너뛴다. 예를 들어 매월 30일은 2월에 실행하지 않고, 31일은 2월이나 30일인 달에 실행하지 않는다. `매월 말일` 규칙은 매달 실제 마지막 날에 실행한다. 특정 날짜 1일은 별도 월초 설정 없이 1일 선택으로 표현한다. 회차가 없는 달에는 이전 미완료 회차를 자동 종료하지 않고, 다음 실제 회차 도래 때 기존 `MISSED` 규칙을 적용한다([ADR-029](../decisions/ADR-029-monthly-recurrence-dates.md)).

## 후속 결정 — 반복 종료 조건

- 날짜: 2026-11-09
- 결정: `D-062` (`Q-040` 해결)

사용자는 추천안에 동의했다. 반복 종료일은 선택 사항으로 지원하고, 기본값은 무기한 반복으로 둔다. 종료일은 반복 규칙의 시간대에 따른 현지 날짜이며 그 날짜의 회차까지 포함한다. 종료일 뒤에는 새 회차와 알림을 만들지 않는다. 마지막 미완료 회차는 종료일만으로 완료·놓침 처리하지 않고, Reminder도 자동 보관·삭제하지 않는다. 반복 횟수 제한은 MVP에서 제외한다([ADR-030](../decisions/ADR-030-recurrence-end-date.md)).

## 후속 결정 — 반복 Reminder의 수정 범위 선택

- 날짜: 2026-11-09
- 결정: `D-063` (`Q-041` 해결)

사용자는 반복 Reminder를 수정할 때 사용자가 적용 범위를 고르도록 하는 추천을 선택했다. 저장 전에 `이번 회차만`, `이번 회차와 이후 회차`, `전체 반복` 팝업을 표시한다. 첫 선택은 RecurrenceRule을 바꾸지 않고 해당 Occurrence만 예외 수정한다. 둘째 선택은 선택된 회차와 이후에 적용하고 이전 회차는 유지한다. 셋째 선택은 과거를 포함한 시리즈 전체의 변경 가능한 데이터를 수정한다. 어느 선택이든 Occurrence identity, 완료 상태, 완료자·완료 시각과 기존 감사 기록은 유지한다. 반복 규칙 자체는 둘째·셋째 선택에서만 수정할 수 있다([ADR-031](../decisions/ADR-031-recurring-edit-scopes.md)).

## 후속 결정 — DST 전환 시 반복 시각

- 날짜: 2026-11-09
- 결정: `D-064` (`Q-042` 해결)

사용자는 한국에서 DST를 거의 사용하지는 않지만 일반적으로 쓰는 정책을 따르자고 동의했다. RecurrenceRule의 IANA time zone에서 DST 시작으로 현지 시각이 사라지면 전환 gap 길이만큼 앞으로 이동해 한 번 실행한다(예: `02:30`이 사라지면 `03:30`). DST 종료로 시각이 두 번 있으면 먼저 발생한 instant에서 한 번만 실행한다. 정책은 [ADR-032](../decisions/ADR-032-recurrence-dst-resolution.md)에 기록했다.

## 시간대·다국어 설계 기준

- 날짜: 2026-11-09
- 설계 기준: `D-065`

시간대별 실행과 다국어 지원은 설계에 포함한다. 일정은 IANA time zone과 UTC instant로 처리하고 사용자 표시 시간대와 recurrence 실행 시간대를 분리한다. UI와 시스템 문구는 locale resource로 분리하며 API는 locale-neutral code를 반환한다. 사용자가 작성한 Reminder 문구는 자동 번역하지 않는다. 시간대와 locale의 공통 정책은 [ADR-033](../decisions/ADR-033-time-zones-and-localization.md)에 기록했다.

## 후속 결정 — MVP 한국어·영어 지원

- 날짜: 2026-11-09
- 결정: `D-066` (`Q-043` 해결)

사용자는 MVP부터 한국어와 영어 UI를 함께 지원하기로 했다. 언어는 개인 설정에서 선택하고 기본값은 `ko-KR`이다. 영어 locale은 `en-US`로 두며, UI·시스템 문구, 날짜·시간·숫자는 선택 locale에 맞춘다. 사용자 작성 Reminder 문구는 번역하지 않는다([ADR-034](../decisions/ADR-034-mvp-language-support.md)).

## 후속 결정 — 데이터 내보내기 고려와 구현 시점

- 날짜: 2026-11-09
- 결정: `D-067` (`Q-009`의 내보내기 범위 해결)

사용자는 데이터 내보내기를 고려해 설계하되 구현은 후속으로 미루기로 했다. 초기 내보내기 포맷은 JSON을 우선 검토하고, 도메인 데이터를 안정적인 ID와 정규화된 관계로 유지한다. MVP에는 내보내기 UI/API를 넣지 않는다. 내보낼 데이터·권한·민감 항목은 기능을 구현할 때 결정한다. 계정·가구 종료 시 데이터 삭제·보존 정책은 `Q-009`에 남긴다([ADR-035](../decisions/ADR-035-data-export-deferred.md)).

## 후속 결정 — 계정 삭제와 가구 종료 분리

- 날짜: 2026-11-09
- 결정: `D-068` (`Q-009` 해결)

사용자는 계정 삭제와 가구 종료를 분리하는 추천안에 동의했다. 계정 삭제 시 Firebase 연결·개인 프로필·세션·기기 token을 제거하고 해당 사용자의 Membership와 Assignment를 정리한다. 다른 구성원의 담당 관계와 알림은 유지한다. Household Reminder와 업무 이력은 남기되 삭제 계정의 요청자·완료자·행위자 참조와 이름을 제거하고 이력에는 `탈퇴한 구성원`으로 표시한다. 담당자가 남지 않으면 현재·미리 생성된 회차를 보존하고 알림·새 회차 생성을 멈춘 뒤 재지정 시 `D-060`의 회차 건너뜀·미래 회차 재개 규칙을 적용한다. 계정 삭제 후 Admin이 0명이 될 가구가 있다면 다른 구성원에게 Admin을 넘기거나 해당 가구를 먼저 종료한다.

Admin은 구성원이 남아 있더라도 가구를 종료할 수 있고 다른 구성원의 동의는 요구하지 않는다. 확인 화면에서 구성원 수와 전체 구성원의 접근 상실, 공유 데이터의 앱 내 복구 불가 삭제를 명시한다. 종료 즉시 접근과 초대를 차단하고 Household 소유 Reminder·회차·Trigger·Assignment·이력·설정·기기별 동기화 상태·미전달 알림 작업을 제거한다. 구성원 계정은 다른 Household에서 계속 쓸 수 있게 둔다. 종료 signal과 앱 재실행 시 안내는 best-effort로 제공한다. 운영 DB에서 즉시 제거하고 계정·가구 종료 tombstone과 암호화 백업은 최대 30일 보존한다. 사용자가 마지막 구성원인 가구는 계정 삭제와 함께 종료한다. 셀프서비스 화면/API는 MVP에서 제외하고, 상용 공개 전 개인정보 처리와 백업 복원 절차를 검토한다([ADR-036](../decisions/ADR-036-account-and-household-closure.md)).

## 설계 범위 정리 — 로그인 제공자와 iOS

- 날짜: 2026-11-09
- 상태: MVP 범위 밖; 인터페이스 경계 유지

사용자는 다른 로그인 제공자와 iOS 지원은 나중에 검토하고, 현재는 확장 가능한 경계만 설계에 유지하기로 했다. MVP는 Google provider와 Android 앱에 집중한다. 인증은 provider-neutral `IdentityProvider` port 뒤에 두고, iOS/APNs 및 OS별 알림·위치 기능은 기존 platform-neutral capability port에 adapter를 추가할 수 있게 유지한다(`D-024`, `D-006`, `D-052`). 추가 로그인 제공자 범위와 iOS push 설계는 각각 `Q-030`, `Q-019`에 남긴다.

## 후속 결정 — Reminder 생성 기본값

- 날짜: 2026-11-09
- 결정: `D-069`

사용자는 Reminder 생성 때 요청자 기본값을 작성자로 두고, 담당자는 로그인한 자신을 미리 선택하는 추천을 선택했다. `created_by`는 항상 실제 작성자인 로그인 사용자로 자동 기록한다. 요청자는 같은 household의 다른 활성 구성원으로 바꿀 수 있고, 담당자는 한 명 이상을 유지하면서 다른 활성 구성원을 추가·제거해 여러 명으로 지정할 수 있다. 요청자와 담당자는 별개이며 생성 후에도 수정할 수 있다. 구현은 [ADR-037](../decisions/ADR-037-reminder-creation-defaults.md)을 따른다.

## 후속 결정 — 개발 루프 테스트와 환경 분리

- 날짜: 2026-11-09
- 결정: `D-070`

사용자는 unit·integration test를 매 개발 루프에서 실행하는 방향을 선택했다. TypeScript typecheck, 관련 unit test, NestJS·Prisma·SQLite API integration test를 빠른 gate로 두고, Kotlin native module을 변경한 루프에는 JVM unit test도 포함한다. Development·Test·Production은 분리하며 자동 테스트는 임시 DB, synthetic fixture와 fake adapter를 사용한다. 복구 테스트는 매 루프에 넣지 않고 복구나 운영 절차를 변경할 때만 별도로 검토한다. 하네스는 코드 저장소 scaffold가 생길 때 단일 실행 명령과 운영 환경 오접속 방지 검사를 포함해 작게 만든다. 자세한 경계는 [테스트 전략](../08-test-strategy.md)에 기록했다.

## 후속 결정 — 테스트 우선 구현과 리뷰

- 날짜: 2026-11-09
- 결정: `D-071`

코드 동작을 추가·변경할 때 관련 요구사항과 수용 기준에 연결된 테스트를 먼저 작성하고, assertion이 잘못된 동작을 잡는지 확인한 뒤 구현하기로 했다. 가능하면 구현 전에 테스트 실패를 확인한다. 작업 에이전트가 테스트와 구현을 함께 검토하므로 사용자는 일반적인 작업마다 별도로 테스트 코드를 리뷰하거나 승인할 필요가 없다. 제품 정책이 모호하거나 기존 결정과 충돌할 때만 사용자에게 확인한다. 절차는 [테스트 전략](../08-test-strategy.md)에 기록했다.

## 후속 결정 — 앱 진입 기본 목록

- 날짜: 2026-11-09
- 결정: `D-072` (`Q-044` 해결)
- 질문 (`Q-044`): 앱을 열었을 때 어떤 업무 목록을 기본으로 보여줄지, 기한별 섹션으로 나눌지 일정순으로 정렬하고 상태 뱃지를 붙일지?

사용자는 앱을 열었을 때 `내 할 일`을 기본으로 보여주고, 필요하면 가구 전체로 전환하는 추천을 선택했다. 섹션은 기한 초과·오늘·예정 순서로 두고, 시간 Trigger는 각 섹션 안에서 예정 시각이 빠른 순으로 정렬한다. 장소 Trigger는 기한이 없으므로 예정 섹션에 장소 조건으로 표시한다. 각 항목은 `D-036`의 Occurrence 상태 뱃지를 유지한다. 두 보기의 그룹·정렬 규칙과 행·섹션 UI는 모듈로 분리해 재사용하고, 나중에 목록 구성을 바꾸기 쉽게 한다. 완료·놓침 이력과 보관함은 별도 화면이다. 상세 수용 기준은 [제품 요구사항](../01-product-requirements.md#6-수용-기준)에 기록했다.

## 후속 결정 — Android 알림 설정 소유권

- 날짜: 2026-11-09
- 결정: `D-073` (`Q-045` 해결)
- 질문 (`Q-045`): 시간·장소 알림의 채널 켜기/끄기와 조용한 시간을 앱 안에서 별도로 제공할지, Android OS 설정에 맡길지? 장소 감지 즉시 알림 원칙은 어떻게 유지할지?

사용자는 알림 설정을 Android OS가 관리하고 앱 안에 중복 설정을 만들지 않는 추천을 선택했다. Android 알림은 시간·장소 채널로 나누며 사용자는 Android 설정에서 채널 on/off, 표시·소리 및 방해 금지를 관리한다. Notify Me 설정 화면은 해당 설치의 권한·채널 상태를 안내하고 OS 설정으로 이동하는 기능만 제공한다. 앱은 예정 시각 또는 장소 조건 감지 직후 알림을 게시하며(`D-042`), 실제 표시·소리 여부는 OS 설정에 따른다. 적용 기준은 [제품 요구사항](../01-product-requirements.md#6-수용-기준)과 [설정 설계](../05-settings-and-feature-configuration.md)에 반영했다.
