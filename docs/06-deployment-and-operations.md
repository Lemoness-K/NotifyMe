# 배포 및 운영 설계 (초안)

상태: 초안
기준일: 2026-09-12 (Asia/Seoul)
최근 갱신일: 2026-11-10

이 문서는 가정과 실제 점검 결과를 구분해, 가정용 Raspberry Pi 배포에서 향후 외부 서비스로 확장하기 위한 운영 방향을 기록한다. 이 문서 작성 과정에서는 호스트에 패키지, 서비스, 네트워크 설정 또는 데이터 변경을 수행하지 않았다.

개발 루프의 자동 검증과 환경 분리 기준은 [테스트 전략](./08-test-strategy.md)을 따른다. 아래 단계의 기기·RPi·복구 검증은 매 개발 루프에 반복하는 항목이 아니라 기능 검증 또는 운영 준비 항목이다. 복구 리허설은 백업·복구 변경이나 운영 준비가 필요할 때 별도로 수행한다.

표기 규칙:

- `[확인]`: 2026-09-12에 호스트에서 읽기 전용으로 확인한 값
- `[가정]`: 현재 구현 전까지 임시로 두는 운영 가정
- `[미결정]`: 기술 선택 또는 제품 요구사항 인터뷰가 필요한 항목

## 2. 현재 운영 범위와 미설치 상태

현재 목표는 Raspberry Pi 서버를 MVP부터 인터넷 HTTPS로 제공하고, 집 안팎의 클라이언트가 상시 연결되어 있다고 가정하는 것이다(`D-011`). Android 앱은 시간·위치 시스템 알림을 제공하고, FCM은 담당자 기기의 변경 동기화를 알리는 비사용자용 신호로 사용한다(`D-046`). Play Store 업로드는 범위에 넣지 않는다.

다음 항목은 이 문서 작성 시점에 아직 설치하거나 변경하지 않았다.

- Docker 및 Docker Compose 설치
- 애플리케이션, 데이터베이스, 리버스 프록시, systemd 서비스
- 설치형 Android 셸, 기기 로컬 예약·지오펜스 및 시스템 알림 연동
- Node 의존성 및 전역 패키지
- microSD 교체 또는 SSD 연결/이동
- 라우터 포트 포워딩, DDNS, 방화벽 설정
- 백업 작업, 모니터링, 외부 알림 연동

## 3. 배포 토폴로지 초안

### 3.1 MVP: 인터넷 접속 배포

`D-057`에 따라 DDNS와 라우터 포트 포워딩을 이용한 목표 구성은 다음과 같다. 실제 도메인과 네트워크 환경은 배포 단계에서 확인한다. 이 설계 문서 작성 과정에서는 라우터나 호스트 설정을 변경하지 않았다.

```text
외부 브라우저 / Android 앱
           |
  인터넷 HTTPS / DDNS
           |
가정용 라우터 (TCP 80/443)
           |
 Caddy (자동 HTTPS ingress)
     |               `-- API reverse proxy --> NestJS API
     `-- React 정적 build                       |-- SQLite
                                               `-- Worker
                                                    `-- FCM ChangeSignal
```

Caddy, React 정적 build, NestJS API, SQLite와 Worker는 Raspberry Pi 5의 Ubuntu에서 실행한다.

공유 Web UI와 Android 셸은 Caddy를 통해 인터넷 HTTPS API를 사용한다. Caddy는 DDNS hostname에 대한 HTTPS 인증서를 자동 발급·갱신하고 HTTP 접속을 HTTPS로 redirect하며, React 정적 build를 제공하고 API 요청을 NestJS로 전달한다(`D-057`). 이를 위해 실제 hostname이 공인 인터넷에서 RPi를 가리키고 외부 TCP 80/443이 Caddy에 도달해야 한다. Android의 정확 알람 접근 상태와 거부 시 부정확 알람 fallback, 백그라운드 위치 권한 및 재부팅 후 재등록을 처리한다(`D-047`). Android 설정에서 force-stop한 동안의 background 알림은 보장하지 않으며, 사용자가 앱을 다시 열면 full sync와 예약 복구를 수행한다(`D-050`). 서버는 이력의 기준 데이터다. FCM은 영향을 받는 설치에 revision 기반 ChangeSignal을 전달하며 사용자 알림으로 표시하지 않는다(`D-046`). Outbox 발송 오류는 24시간 exponential backoff와 TTL로 제한하고 이후 client sync에 맡긴다(`D-049`).

개발 초기에는 단일 Node 프로세스(웹/API와 서버 작업 포함)를 사용할 수 있으나, 서버 작업과 Android 로컬 예약이 같은 알람을 중복 처리하지 않도록 책임 범위와 이벤트 ID를 먼저 정한다. 스케줄 작업이 중복 실행되지 않도록 단일 실행자 또는 분산 잠금 정책도 필요하다.

NestJS API·Worker의 장기 실행 프로세스는 호스트 `systemd` 서비스로 직접 실행한다. 부팅 시 자동 시작하고 비정상 종료 때 `systemd`가 재시작하며, 앱 표준 출력·오류는 `journald`에서 확인한다(`D-077`, `PR-AC-062`, `ADR-038`). 운영자는 서비스 상태와 최근 로그, 로컬 전용 헬스체크, 디스크·메모리 사용량과 백업 결과를 명령으로 점검한다. 헬스체크는 Caddy의 공개 경로에 연결하지 않고 별도 대시보드도 두지 않는다. MVP에는 Docker를 설치하지 않는다.

추후 Docker Compose 이전을 막지 않도록 앱 실행환경과 영속 데이터·설정·비밀값을 분리한다. 구체적인 `systemd` unit, 실행 사용자, 영속 경로, 환경 파일, 헬스체크 주소와 명령은 `DS-008`에서 확정한다. Docker 이전은 별도 변경으로 다루며, 전환 때는 서비스를 멈추고 SQLite backup/restore와 기동 smoke를 검증한다.

MVP 데이터 저장소는 SQLite다(`D-053`). 별도 DB server를 설치하지 않고 SQLite 파일을 RPi의 코드 외부 로컬 영속 경로에 둔다. API와 Worker의 write transaction은 짧게 유지하고 MVP Worker는 하나만 실행한다. 여러 worker·서버 인스턴스나 상용 동시성 요건이 구체화되면 PostgreSQL 전환의 비용과 migration을 다시 평가한다. SQLite DB를 네트워크 파일시스템에 두지 않는다.

알람은 서버의 Asia/Seoul 기준 시각과 다음 실행 시각을 정확히 기록하고, 담당자 Android 기기에 로컬 예약 또는 지오펜스를 등록한다. 반복 알람 생성과 기기 예약 등록은 재시작·재부팅·재시도 때 중복 인스턴스를 만들지 않도록 멱등성을 보장해야 한다. 위치 알림은 지오펜스 진입·이탈과 권한 상태를 기록하며, 시간·위치 조건이 충족되면 Android 시스템 알림을 표시한다. FCM ChangeSignal은 알림을 표시하지 않고 변경된 revision을 fetch해 기기 상태를 reconcile하게 한다(`D-046`).

### 3.2 MVP 외부 경로: DDNS 및 포트 포워딩

외부 브라우저와 Android 앱 모두 같은 Caddy ingress를 사용한다.

```text
외부 브라우저 / Android 앱
    |
DDNS hostname + HTTPS
    |
가정용 라우터(TCP 80/443만 포워딩)
    |
Caddy(자동 HTTPS, 정적 파일 제공, API reverse proxy)
    |-- React 정적 build
    `-- API reverse proxy --> NestJS API --> SQLite / 작업 실행기
```

공개 ingress는 Caddy 하나로 제한한다. 라우터에서는 TCP 80/443만 Caddy로 전달하고 NestJS, SQLite, 관리 포트는 직접 노출하지 않는다(`D-057`). 공인 HTTPS 인증서는 Caddy가 자동으로 발급·갱신한다. 앱 개발 서버를 공인 인터넷에 직접 노출하지 않고 공개 전 인증·인가, 업데이트, 요청 제한, 백업·복구를 검증한다. DDNS 제공자와 hostname은 아직 결정하지 않았으며 실제 설정은 배포 작업에서 수행한다.

## 4. 저장장치·백업 운영 방침

현재 루트가 microSD이므로 다음 위험을 설계에 반영한다.

- DB, 로그, 반복적인 상태 업데이트가 누적되면 microSD 쓰기 수명과 파일시스템 손상 위험이 커진다.
- 전원 차단이나 강제 재부팅 시 DB 파일과 스케줄 상태가 함께 손상될 수 있다.
- 루트 파티션의 여유 공간 22 GB는 초기에는 충분하지만 로그·첨부파일·백업을 같은 파티션에 계속 쌓으면 빠르게 줄어든다.
- Swap이 없으므로 메모리 부족 시 서비스가 불안정해질 수 있다. 무작정 swap을 추가하지 말고 실제 메모리 압박을 관찰한 뒤 결정한다.

권고 순서는 다음과 같다.

1. 안정화 단계에서는 애플리케이션 데이터, 로그, 백업 파일을 코드와 분리된 경로에 두고 로그 보관 기간과 용량 상한을 설정한다.
2. 지속 운영 전에는 USB 3 SSD를 주 저장장치 또는 최소한 DB·데이터 전용 저장장치로 검토한다. 전원 공급이 안정적인 케이스와 안전한 종료 절차를 함께 준비한다.
3. SSD를 사용하더라도 동일 장치에만 보관하지 않는다. 외부 저장장치 또는 다른 호스트로 암호화된 정기 백업을 복사하고, 복호화 key를 백업 본체와 분리해 보관하며 주기적으로 실제 복원을 시험한다.
4. 최소 운영 기준은 일일 DB 백업, 주기적인 전체 백업, 백업 성공/실패 기록이다. 암호화된 운영 백업은 순환 보관하고 보존기간은 최대 30일로 제한한다(`D-058`). 상업화 전에는 오프사이트 백업과 복구 목표(RPO/RTO)를 정한다.
5. 별도 파일·장치·서비스에 보관하는 백업은 암호화하고 key를 백업 본체와 분리한다. RPi 서비스는 수동 잠금 해제 없이 자동 시작한다. 전체 디스크 암호화는 현재 위협 모델에 포함하지 않으며, 운영 DB 암호화는 DB 제품과 구체적인 위험 검토 후 선택한다(`D-025`, `NFR-SEC-006`, `NFR-REL-007`).

SQLite WAL online 백업은 Online Backup API 또는 이에 준하는 일관된 snapshot 방식을 사용한다. 활성 DB의 main file만 임의 복사하지 않는다. 복원은 별도 경로에서 파일 무결성, migration, 앱 기동과 기본 조회를 확인한다. 서비스를 다시 열기 전에 유효한 영구 삭제 tombstone을 복원 snapshot에 재적용해 삭제 항목이 되살아나지 않는지 확인한다([SQLite Backup API](https://www.sqlite.org/backup.html), `D-053`, `D-058`).

현재 SSD 연결, 백업 장치, 백업 스케줄은 준비되지 않았다.

## 5. 운영 및 보안 원칙

- 앱, DB, 작업 실행기는 전용 운영 사용자와 최소 권한으로 실행한다.
- Firebase service account, 세션 signing key, DDNS/TLS 자격증명은 저장소와 문서에 넣지 않는다. 서비스 운영 사용자만 읽을 수 있는 보호된 credential 파일 또는 OS 비밀 저장 방식을 사용한다.
- 인터넷 접근에 대해 사용자 계정을 인증하고 가구 구성원 권한을 서버에서 검증한다. 개인 일정과 집안일 내용은 민감정보로 취급한다.
- RPi OS 기본 시간대는 운영 표시용 `Asia/Seoul`로 둘 수 있지만, 업무 일정 계산은 OS 기본 시간대를 암묵적으로 사용하지 않는다. API/Worker는 household 또는 반복 규칙에 명시된 IANA zone과 UTC instant를 사용하고, NTP 동기화 실패·시계 변경을 감지한다(`D-064`, `D-065`).
- 서비스 재시작 후 미완료 알람, 완료 이력, 반복 일정의 다음 발생 시각이 보존되는지 확인한다.
- 서비스 상태와 오류 로그, 로컬 헬스체크, 디스크 사용량, 메모리, 백업 결과는 명령으로 확인한다. MVP 운영 대시보드는 두지 않는다(`D-077`, `PR-AC-062`).
- 주간 운영 요약과 감지 즉시 생성되는 장애 기록은 각각 선택적으로 활성화하며, 운영 호스트의 명령과 journald에서 확인한다(`D-092`, `D-098`). 외부 수신 채널과 독립 호스트 장애 감지는 후속이다.
- 외부 공개가 필요해지면 라우터와 OS의 방화벽 정책, HTTPS 인증서 갱신, 취약점 업데이트, 로그인 시도 제한을 함께 운영한다.

SQLite 데이터베이스는 선택됐다(`D-053`). Web UI는 React Router + Vite SPA build를 사용한다(`D-054`). API는 Node.js runtime 위에서 NestJS framework로 실행하고(`D-055`), Prisma ORM 7과 better-sqlite3 driver adapter로 SQLite에 접근한다(`D-056`). 외부 ingress와 HTTPS는 Caddy로 정했다(`D-057`). MVP 프로세스 실행과 최소 관측은 `systemd`·`journald`·명령 기반 점검을 사용한다(`D-077`, `PR-AC-062`, [ADR-038](./decisions/ADR-038-systemd-rpi-service-management.md)). 실제 호스트 Node.js 버전과 ARM64 native adapter 호환성은 구현 착수 시 확인한다.
